# Specification for reproducing the four Cisco IP SLA ICMP operations on Linux

Cross-checking Cisco's official IP SLAs Configuration Guide and IP SLAs Command Reference against CISCO-RTTMON-MIB / CISCO-RTTMON-TC-MIB / CISCO-RTTMON-ICMP-MIB, **the four operations icmp-echo, path-echo, icmp-jitter and path-jitter can be pinned down precisely enough to implement: the default values and ranges of their parameters, the ordering rule `(frequency seconds) > (timeout milliseconds) > (threshold milliseconds)`, a state machine that converges on the three states pending / inactive / active, the RttResponseSense return codes (0-38), a three-layer data model of hourly aggregated statistics, snapshot history and enhanced history, the threshold reaction rule of one notification per rising->falling transition, and the structure of the MIB tables under 1.3.6.1.4.1.9.9.42**. The default values at the core of an implementation are frequency **60 s**, timeout **5000 ms**, threshold **5000 ms**, request-data-size **28 bytes** (IP 20 + ICMP 8 + internal timestamps 8 + 28 = a **64-byte** IP packet), icmp-jitter sends **ICMP Timestamp Request/Reply (Type 13/14), 10 packets x 20 ms**, the path operations discover the path like traceroute and then send an echo per hop, statistics are kept for **2 hours**, history buckets **15** (the "50" in the Command Reference text contradicts the MIB DEFVAL and every show output), and the maximum is **2000 operations**. Conversely, Cisco does not publish the layout of the 8-byte internal timestamp in the ICMP echo payload, the probe type used for path discovery, the rule for accepting or rejecting one-way delay samples in icmp-jitter, or how overThreshold is treated in the Number of successes of `show ip sla statistics`, among others; the implementer must decide these. This document explicitly separates behavior documented by Cisco (primary sources), secondary sources such as output from real devices, and this document's own inferences, and ends with guidance for a Linux ICMP implementation and a list of undocumented items.

Conventions: CLI syntax, show output, MIB object names and RFC terms are kept in English. Sources are given as `([label](URL))`, and the labels correspond to the source keys at the end. **Secondary sources** (captures from real devices by parties other than Cisco, etc.) and **inferences** (interpretations this document derives from the documentation) are marked as such in the text.

## Only icmp-jitter uses ICMP Timestamp; the other three operations time an Echo Request/Reply round trip

The four operations split in two by "what they send and what they measure". icmp-echo and path-echo measure round-trip time (RTT) with the Echo Request/Echo Reply of RFC 792. The TC-MIB defines RttMonRttType `echo` as "a timed echo request/response operation directed at the 'RttMonTargetAddress'" and `pathEcho` as "perform path discovery to the 'RttMonTargetAddress', then it will perform a timed echo request/response operation directed at the each hop along the path", and describes the protocol `ipIcmpEcho` as "uses Echo Request/Reply as defined in RFC792 for Internet Protocol networks" ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my)). Only icmp-jitter uses "ICMP Timestamp Request (Type 13) and an ICMP Timestamp Reply (Type 14)" ([CG-JIT-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_jitter.html)); in the TC-MIB it corresponds to `icmpjitter(16)` "perform delay variance analysis using ICMP timestamp packets" and the protocol `icmpJitterAppl(34)` "uses ICMP Timestamp for packet transfer to measure jitter" ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my)). path-jitter is described as "uses ICMP echoes to determine the response times, packet loss and approximate jitter values for each hop" ([CG-PJ-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_pathjitter.html)) and uses Echo, not Timestamp. What the four operations have in common is that none of them needs the IP SLAs Responder, which is the decisive difference from the UDP operations ([CG-ECHO-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_echo.html), [CG-JIT-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_icmp_jitter.html)).

### icmp-echo measures "from sending the request to receiving the reply" in ms, and its default 28 bytes make a 64-byte IP packet

Cisco defines the ICMP Echo operation as "Response time is computed by measuring the time taken between sending an ICMP Echo request message to the destination and receiving an ICMP Echo reply", and states "The IP SLAs ICMP Echo operation conforms to the same IETF specifications for ICMP ping testing and the two methods result in the same response times" ([CG-ECHO-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_icmp_echo.html)). The requirement on the destination is "We recommend using a Cisco networking device as the destination device although any networking device that supports RFC 862, Echo protocol, can be used"; it cites RFC 862, but what is actually used is ICMP, and "There is no need to configure an IP SLAs responder on the destination device" is stated explicitly ([CG-ECHO-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_icmp_echo.html), [CG-ECHO-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_echo.html)). The Japanese edition translates this as (rendered back into English here) "The response time is calculated by measuring the time from sending an ICMP echo request message to the destination until receiving an ICMP echo reply" ([JA-ECHO](https://www.cisco.com/c/ja_jp/td/docs/ios-xml/ios/ipsla/configuration/xe-16-10/sla-xe-16-10-book/sla-xe-16-10-book_chapter_01111.html)).

The definition of packet size is consistent between the CLI and the MIB. The Command Reference states "The default request packet data size for an ICMP echo operation is 28 bytes. ... This data size is the payload portion of the ICMP packet, which makes a 64-byte IP packet" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)), and the MIB's `rttMonEchoAdminPktDataRequestSize` is "For non-ARR protocols' RTT request/responses, this value represents the native payload size. ... For echo probes the total packet size = (IP header(20) + ICMP header(8) + 8 (internal timestamps) + request size). For echo, pathEcho and pathJitter default request size is 28. ... The minimum request size for echo, pathEcho and pathJitter is 28 bytes", with SYNTAX `Integer32 (0..16384)`, UNITS octets, DEFVAL { 1 } ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). Therefore **20 + 8 + 8 + 28 = 64 bytes** is the default on-wire size, and with `request-data-size N` the ICMP data part is 8 + N bytes and the IPv4 packet 36 + N bytes (generalizing this formula, and that IPv6 gives 40 + 8 + 8 + N, are **inferences** of this document; Cisco does not restate the formula for IPv6). On the reply side, `rttMonEchoAdminPktDataResponseSize` is "For non-ARR RTT request/response (i.e. ipIcmpecho) this value will be set by the agent to match the size of rttMonEchoAdminPktDataRequestSize", so an echo of the same size as the request is expected ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). `show ip sla configuration` displays this value as "Request size (ARR data portion): 28" ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)). The CLI's `request-data-size bytes` says only "Range is from 0 to the maximum supported by the protocol" and, for the default, "varies depending on the type of IP SLAs operation ... See the CISCO-RTTMON-MIB documentation", so the conflict between the MIB's minimum of 28 bytes and the CLI's "from 0" is unresolved ([CR-R](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_r1.html)).

On how timestamps are taken, Cisco says that with the Responder enabled four timestamps TS1-TS4 are taken and "the same principle is applied by IP SLAs on the source device where the incoming time stamp 4 (TS4) is also taken at the interrupt level to allow for greater accuracy", while stating plainly that ICMP-based operations "can compensate for source processing delay but cannot compensate for target processing delay" ([CG-OV-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_overview-0.html), [CG-PJ-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_pathjitter.html)). The byte layout, endianness and epoch of the "8 (internal timestamps)" in the payload, and whether the sequence number is placed in the ICMP header's Identifier/Sequence or in the data part, are not published. The Wireshark wiki (**secondary source**) calls Cisco IP SLA "It is Cisco proprietary protocol, and not all aspects are yet fully reverse engineered" and has no information on ICMP echo / path echo ([WS-WIKI](https://wiki.wireshark.org/Cisco-IPSLA)).

Data verification is enabled with `verify-data` (`no verify-data`); the default is "Data is not checked for corruption", the applicable modes are ICMP echo, ICMP path echo, ICMP path jitter, multicast UDP jitter, UDP echo and UDP jitter, and the caution reads "Use the verify-data (IP SLA) command only when data corruption may be an issue. Do not enable this feature during normal operation because it can cause unnecessary network overhead" ([CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)). The MIB's `rttMonCtrlAdminVerifyData` (DEFVAL false) says "the resulting data in each RTT operation is compared with the expected data. This includes checking header information (if possible) and exact packet size. Any mismatch will be recorded in the rttMonStatsCollectVerifyErrors object", and ends with the sentence "This object is only applicable to SNA protocols", which contradicts the CLI ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The return code on a mismatch is `verifyError(9)` "a completed operation was received, but the data it contained did not match the expected data; no completion time recorded" ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my)), and `rttMonStatsCollectVerifyErrors` specifies "The completion time of these operations are not accumulated, nor do they increment rttMonStatsCaptureCompletions" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). Since an ICMP destination only returns the received payload as is, verify-data can only be implemented as a byte-by-byte comparison with the sent data (and a size comparison) (**inference**).

The payload pattern differs between documents. The Command Reference's `data-pattern hex-pattern` says "The default hex-pattern is ABCD" and "The data-pattern command is supported by the IP SLAs User Datagram Protocol (UDP) echo operation only" ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)), but the ICMP Echo configuration procedure includes in Step 5 "`data-pattern hex value` ... (Optional) Sets the hexadecimal value for data pattern. The range is 0 to FFFFFFFF", with the prompt example `Device(config-ip-sla-echo)# data pattern FFFFFFFF` ([CG-ECHO-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_icmp_echo.html), [CG-ECHO-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_echo.html)). On a real IOS XE 16.9 device (**secondary source**) the icmp-echo submode has `data-pattern`, and `show ip sla configuration` shows "Data pattern: 0xABCDABCD" ([FRR](https://fastreroute.com/cisco-ip-sla-ios-xe/)). The MIB has no object for the data pattern ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

A sequence anomaly is `sequenceError(8)` "a completed operation did not contain the correct sequence id; no completion time recorded" ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my)), and the causes listed for `rttMonStatsCollectSequenceErrors` are "a duplicate packet was received - a response was received after it had timed-out - a corrupted packet was received and was not detected" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). In other words, Cisco's accounting discards a reply that arrives after the timeout as a sequence error instead of attributing it to the next cycle. For the source address, when `source-ip` is not specified "IP SLAs chooses the IP address nearest to the destination", and nothing more than "Specifies the source interface for the operation" is written about how `source-interface` is chosen ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)).

### path-echo discovers the path with traceroute, then sends an echo to each hop, and records per (path, hop)

Path Echo "measures end-to-end and hop-by-hop response time between a Cisco device and other devices using IP", and is explained as "The ICMP Path Echo operation determines this hop-by-hop response time ... by discovering the path using the traceroute facility. ... A ping is then used to measure the response time between the source IP SLAs device and each subsequent hop in the path to the destination IP device" ([CG-PATH-XE16](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/xe-16/sla-xe-16-book/sla-icmp-pathecho.html)). The TC-MIB warns "NOTE: The 'pathEcho' time delay operation is a heuristic measurement because an intermediate hop may forward the different echo request/response at different rates. Thus the time delay difference between two hops along a path may contain very little 'true' statistical meaning" ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my)). The IOS XE 16.9 CLI help (**secondary source**) shows path-echo as "Path Discovered ICMP Echo Operation" ([FRR](https://fastreroute.com/cisco-ip-sla-ios-xe/)).

One cycle is one "operation" in the MIB, and `rttMonCtrlOperNumRtts` specifies "when rttMonCtrlAdminRttType is set to 'pathEcho' this value will be incremented by one and not for very every hop along the path" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The dimensions of the statistics are path and hop: `rttMonStatisticsAdminNumPaths` (1..128, DEFVAL 5) is "the maximum number of statistics paths to record per hourly group ... NOTE: For 'pathEcho' a source to target path will be created to to hold all errors that occur when a specific path or connection has not be found/setup. Thus, it is advised to set this value greater than one. Since this index does not rollover, only the first rttMonStatisticsAdminNumPaths will be kept", and `rttMonStatisticsAdminNumHops` (1..30, DEFVAL 16) says "we can only support 30 hops" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). In the CLI they are `paths-of-statistics-kept size` (default 5, "A path is the route the request packet of the operation traverses ... When the number of paths reaches the size specified, no further path-based information is stored") and `hops-of-statistics-kept size` (default 16), both specific to path echo ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html), [CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)). The path index is "the agent assigns the first instance of a path a value of 1, then second instance a value of 2, and so on", the hop index is "This value shows the order along the path to a target", and the address recorded per sample is "the address of the hop along the path to the rttMonEchoAdminTargetAddress address, including rttMonEchoAdminTargetAddress address" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The memory estimate is "Memory allocation = (160 bytes) * (distributions-of-statistics-kept size) * (hops-of-statistics-kept size) * (paths-of-statistics-kept size) * (hours-of-statistics-kept hours)" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)).

For history, "When the operation type is Internet Control Message Protocol (ICMP) path echo, an entry is created for each hop along the path", and `samples-of-history-kept samples` (default 16, MIB `rttMonHistoryAdminNumSamples` 1..30 DEFVAL 16) sets the number of hops per bucket ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html), [CR-R](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_r1.html), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The note at the top of the MIB module, "For non-connection oriented protocol the initial RTT request/response operation will be preceded with an RTT request/response operation to the target address to force path exploration and to prove connectivity. The History collection table will contain these responses, but the Statistics capture table will omit them to prevent skewed results", specifies that the replies used for path discovery go into the history but are excluded from the aggregated statistics ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

Loose Source Routing is `lsr-path {host name1 | ip-address1} [[hostname2 | ip-address2]... [hostname8 | ip-address8]]`, with "The maximum number of hops you can specify is eight" and the default "LSR path is disabled", and is specific to path echo and path jitter ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). On the MIB side it is represented by the read-only `rttMonEchoAdminLSREnable` (DEFVAL false) and `rttMonEchoPathAdminTable` (`rttMonEchoPathAdminHopIndex` 1..8, "This maximum table size is limited by the size of the maximum number of hop addresses that can fit in an IP header, which is 8") ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). Threshold, timeout and connection-loss reactions apply only to the destination hop: `rttMonReactAdminTimeoutEnable` says "When the RttMonRttType is 'pathEcho' timeouts to intermediate hops will not cause rttMonCtrlOperTimeoutOccurred to change its value", and `rttMonReactOccurred` says "applied only to the rttMonEchoAdminTargetAddress and not to intermediate hops to the Target" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

The official configuration examples are `ip sla 7` / `path-echo 172.29.139.134` / `frequency 30` / `ip sla schedule 7 start-time after 00:00:30 life 300`, and `ip sla 3` / `path-echo 172.29.139.134` / `frequency 10` / `tag SGN-RO` / `timeout 1000` / `ip sla schedule 3 life 25`, described as "The operation attempts to execute three times in 25 seconds (first attempt at 0 seconds)" ([CG-PATH-XE16](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/xe-16/sla-xe-16-book/sla-icmp-pathecho.html)). As an **inference** of this document, one cycle has two stages: (1) path discovery like traceroute, and (2) one timed echo to each discovered hop in turn (applying the same `timeout` and `request-data-size`); if the discovered sequence of hops differs from the known paths, a new path index is assigned, and index 1 doubles as the source-to-target path that collects errors. What Cisco does not document: the probe type used for discovery (UDP or ICMP), the TTL increments, the number of probes per TTL, the timeout during discovery, whether discovery runs every cycle, the number of echoes per hop (the aggregated samples suggest one completion per hop per cycle), whether `hops-of-statistics-kept` limits the discovery depth, and the meaning of the "Packet Interval/Number of Packets: 20 ms/10" line that appears in the official show sample even though it is a path echo ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)).

### icmp-jitter derives per-direction delay, jitter and loss from the three times of ICMP Timestamp (Type 13/14)

Cisco's description is as follows. "IP SLAs ICMP jitter uses a two ICMP time stamp messages, an ICMP Timestamp Request (Type 13) and an ICMP Timestamp Reply (Type 14), to provide jitter, packet loss, and latency", "The ICMP API sends a configurable number of request message packets out of the interface. The data (time stamp) that is received in the request is returned in a reply message packet along with another time stamp. Every packet includes three time stamps: an Originate (sent) Timestamp, a Receive Timestamp, and a Transmit (reply) Timestamp", "IP SLAs utilizes the time stamps to calculate jitter for each direction, based on the difference between interarrival and interdeparture delay for two successive packets. If the difference is positive, it is counted in positive jitter. A negative value is counted in negative jitter", "Each ICMP packet includes a sequence number in its header that is used to count the number of packets received out of sequence on the sender. Both the sequence number and the receive timestamps can be used to calculate out-of-sequence packets on the source-to-destination path", "All timed-out packets are counted towards Packet Loss. Successive packet loss is calculated by counting, and adding, the number of successive dropped packets" ([CG-JIT-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_jitter.html)). Further, "If any packet cannot be sent due to an internal or unexpected error, or because the timerwheel slot containing the packet is missed, it is counted as Packet Skipped. This metric is very important because statistics are measured on sent packets only", and the measured items are "Jitter (source-to-destination and destination-to-source) / Latency (source-to-destination and destination-to-source) / Round-trip time latency / Packet loss / Successive packet loss / Out-of-sequence packets (source-to-destination, destination-to-source, and round-trip) / Late packets" ([CG-JIT-XE16](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/xe-16/sla-xe-16-book/sla-icmp-jitter.html)). The restrictions are "Cisco IOS-XR devices do not support ICMP Timestamp and hence all ICMP jitter operations to these devices fail", "the IP SLAs ICMP jitter operation may provide less accurate measurements because the accuracy of the measurements provided by a non-Cisco destination device cannot be determined", and "Because ICMP packets do not support voice technology, the IP SLAs ICMP jitter operation does not support Mean Opinion Score (MOS), Calculated Planning Impairment Factor (ICPIF), or estimated transmission rating factor (R) reaction configuration capabilities" ([CG-JIT-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_jitter.html)).

The sending pattern is set by `interval milliseconds` "The default value is 20 ms" and `num-packets packet-number` "The default value is 10 packets per operation" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)), and this burst is repeated every `frequency` (default 60 s). The entry for frequency explains, for UDP jitter, "ten packets sent 20 milliseconds apart. This 'payload' is sent when the operation is started, then is sent again 60 seconds later", and the ICMP jitter default is the same 10 x 20 ms ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)). In the MIB they correspond to `rttMonEchoAdminInterval` (`Integer32 (0..60000)` ms, DEFVAL 20, "applicable to jitter probe only") and `rttMonEchoAdminNumPackets` (Integer32, no range constraint, DEFVAL 10) ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

The Timestamp message of RFC 792 consists of Type 13/14, Code 0, Checksum, Identifier (16 bit), Sequence Number (16 bit), and Originate / Receive / Transmit Timestamp (32 bit each). A timestamp is "32 bits of milliseconds since midnight UT"; when the time is not available, "any time can be inserted in a timestamp provided the high order bit of the timestamp is also set to indicate this non-standard value"; and the Identifier and Sequence Number "may be used by the echo sender to aid in matching the replies with the requests" and "may be zero". There is no data part; the message is a fixed 20 bytes ([RFC792](https://www.rfc-editor.org/rfc/rfc792.txt)). This is consistent with `request-data-size` and `verify-data` not existing in ICMP jitter mode ([CR-R](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_r1.html), [CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)).

The jitter arithmetic that Cisco publishes comes from the SAA document for UDP jitter packets: "Jitter from source to destination (JitterSD) = (T6-T2) - (T5-T1)", "Jitter from destination to source (JitterDS) = (T8-T4) - (T7-T3)", with the example "(82 ms - 20 ms) - (60 ms - 0 ms) = 2 ms positive jitter SD" (T1/T5 are the source send times of two consecutive packets, T2/T6 the arrival times at the destination, T3/T7 the reply times at the destination, and T4/T8 the receive times at the source) ([SAA](https://www.cisco.com/c/en/us/support/docs/availability/high-availability/24121-saa.html)). The description of `show ip sla statistics` is "Jitter is interpacket delay variance"; positive jitter is "network latency increases for two consecutive test packets", negative is "network latency decreases" ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)). The latest-result table of the ICMP-MIB has, per direction, Min, Max, Num, Sum and Sum2 of positive / negative (absolute values), `rttMonLatestIcmpJitterAvgJitter` "The average of positive and negative jitter values in Source-to-Destionation and Destination-to-Source direction", `AvgSDJ` / `AvgDSJ`, Sum/Sum2/Min/Max/Avg of the one-way delay and `NumOW` "The number of successful one way trip time measurements", `PktLoss` "The number of packets lost" (no direction), `PktOutSeqBoth` / `PktOutSeqSD` / `PktOutSeqDS`, `PktSkipped`, `PktLateA` "arrived after the timeout", `MinSucPktL` / `MaxSucPktL` "dropped successively", and the RFC 1889 `IAJOut` / `IAJIn` ([ICMP-MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-ICMP-MIB.my)).

One-way delay requires time synchronization. The overview says "to capture one-way delay measurements the configuration of both the source device and target device with Network Time Protocol (NTP) is required. Both the source and target need to be synchronized to the same clock source" ([CG-OV-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_overview.html)), and the UDP jitter chapter writes "Time synchronization is not required for one-way jitter and packet loss measurements. If time is not synchronized between source and target devices, one-way jitter and packet loss data are returned, but values of "0" are returned for the one-way delay measurements" ([CG-UDPJ-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_udp_jitter.html)). However, `clock-tolerance ntp oneway` is "supported by the IP SLAs User Datagram Protocol (UDP) jitter operation only" ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)), and the ICMP jitter chapter says nothing at all about NTP ([CG-JIT-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_jitter.html)). On a real device (**secondary source**), an `icmp-jitter` with the default settings returns "Number Of RTT: 10 RTT Min/Avg/Max: 1/1/1 milliseconds", "Number of Latency one-way Samples: 0", "Number of SD Jitter Samples: 9 / Number of DS Jitter Samples: 9" and "Source to Destination Jitter Min/Avg/Max: 0/1/1": jitter and RTT are reported, but the one-way samples are 0 ([FRR](https://fastreroute.com/cisco-ip-sla-ios-xe/)). A CSR1000V debug (**secondary source**) prints the four times as `STS: 2183208743 RTD: 35723058 STD: 35723058 RTS: 35725395`; the poster points out that STS has the RFC 792 high-order bit set (masked, it is 35725095 ms = 09:55:25.095 UTC) and that the destination's clock was about 2 seconds behind, and the result was "Number Of RTT: 1" and "Number of Latency one-way Samples: 0" ([NSP](https://www.mail-archive.com/cisco-nsp@puck.nether.net/msg67014.html)).

Cisco does not state the arithmetic for the ICMP version, so the following is an **inference** this document derives from the semantics of RFC 792, the SAA formulas and the MIB object definitions. For packet i of a burst, let O_i = the Originate Timestamp written by the source, R_i = the Receive Timestamp written by the destination, T_i = the Transmit Timestamp written by the destination, and A_i = the time the source received the reply (Cisco internal time).

| Metric (inferred) | Formula | Notes |
|---|---|---|
| RTT_i | A_i − O_i | Uses only the source's clock. Whether the destination's processing time (T_i − R_i) is subtracted is undocumented |
| SD one-way delay_i | R_i − O_i | Assumes synchronization with the destination's clock. Meaningless if unsynchronized (real devices show 0 samples) |
| DS one-way delay_i | A_i − T_i | Same as above |
| SD jitter_i | (R_i − R_{i−1}) − (O_i − O_{i−1}) | A constant clock offset cancels out. > 0 is positive, < 0 is negative |
| DS jitter_i | (A_i − A_{i−1}) − (T_i − T_{i−1}) | Same as above |
| Number of jitter samples | Number of consecutive pairs with replies (N − 1 = 9 without loss) | Matches the 9 in real device output. Min is 0, so samples with a difference of 0 are counted too |
| Avg (per direction) | Mean of \|jitter\| over all samples in the direction | A reading of the MIB's "average of positive and negative jitter values" |
| Packet Loss | Number of requests without a reply within the timeout (direction cannot be determined) | Consistent with the reaction element `packetLoss` "The path of the packets is unknown" |
| Packet Late Arrival | Number of replies that arrived after the timeout | MIB "arrived after the timeout" |
| Packet Skipped | Number of packets that could not be sent (excluded from the denominator) | "statistics are measured on sent packets only" |
| Out Of Sequence SD / DS / both | Determine reordering on the SD side, the DS side, or both from the order of the replies' Sequence Numbers and the monotonicity of R_i | Corresponds to the three CLI counters and "(source-to-destination, destination-to-source, and round-trip)" |

RFC 792 timestamps are whole milliseconds, so ICMP jitter statistics are inherently of ms granularity, and an implementation must handle the wrap across midnight at 86,400,000 ms and the high-order bit (the non-standard value flag) (**inference**). What Cisco does not document: the rule for accepting one-way samples (there is no `clock-tolerance`), whether the destination's processing time is subtracted from the RTT, the definition of "Packet Unprocessed" seen in real device output, whether the operation number is carried in the Identifier, whether replies with non-monotonic timestamps are discarded, and whether one-way values are set to 0 or simply not counted when NTP is not synchronized.

### path-jitter is a CLI-only operation that sends N ICMP echoes to each hop after a traceroute, and has no MIB, history or hourly statistics

The syntax is `path-jitter {destination-ip-address | destination-hostname} [source-ip {ip-address | hostname}] [num-packets packet-number] [interval milliseconds] [targetOnly]`, where `num-packets` is "The default value is 10 packets per operation", `interval` is "The default is 20", and `targetOnly` is "Sends test packets to the destination only (path is not traced)". The usage explanation is "If the targetOnly keyword is not used, the IP SLAs ICMP path jitter operation will trace a "hop-by-hop" IP path from the source to the destination and then send a user-specified number of test packets to each hop along the traced path at user-specified time intervals", and the examples are `ip sla 2` / `path-jitter 172.69.5.6 num-packets 50 interval 30` / `ip sla schedule 2 start-time now` ("send 50 test packets to each hop with an interval of 30 ms") and the IPv6 `path-jitter 2001:10:10:10::3 num-packets 50 interval 30` ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). The configuration guide says it "first discovers the hop-by-hop IP route from the source to the destination using a traceroute utility, and then uses ICMP echoes to determine the response times, packet loss and approximate jitter values for each hop along the path", and defines the defaults as N = 10, T = 20 ms, F = 60 s ([CG-PJ-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_pathjitter.html), [CG-PJ-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_icmp_pathjitter.html)). The Responder "does not have to be enabled on either the target device or intermediate devices for Path Jitter operations. However, the operational efficiency may improve if you enable the IP SLAs Responder" ([CG-PJ-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_icmp_pathjitter.html)).

The restrictions are clear: "ICMP-based operations can compensate for source processing delay but cannot compensate for target processing delay", "The jitter values obtained using IP SLAs - ICMP Path Jitter are approximates because ICMP does not provide the capability to embed processing times on devices in the packet", "A path jitter operation does not support hourly statistics and hop information", "Unlike other IP SLAs operations, the ICMP Path Jitter operation is not supported in the RTTMON MIB. Path jitter operations can only be configured using Cisco commands and statistics can only be returned using the show ip sla commands", and "IP SLAs - Path Jitter does not support the IP SLAs History feature (statistics history buckets) because of the large data volume involved with jitter operations" ([CG-PJ-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_pathjitter.html), [CG-PJ-XE3S](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/xe-3s/asr1000/sla_path_jitter.html)). The commands explicitly stated as "not applicable" in path jitter mode are history buckets-kept, history distributions-of-statistics-kept, history enhanced, history filter, history hours-of-statistics-kept, history lives-kept, history statistics-distribution-interval, samples-of-history-kept, lsr-path, tos, threshold and verify-data; the ones listed in the configuration procedure table are `frequency`, `owner`, `request-data-size`, `tag`, `timeout` and `vrf` ([CG-PJ-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_pathjitter.html), [CG-PJ-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_icmp_pathjitter.html)). `vrf` has the additional condition "For ICMP path jitter operations, you must specify the source IP address or hostname when using the vrf command" ([CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)).

The official output example is as follows, listing RTT, jitter and packet values per hop ([CG-PJ-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_icmp_pathjitter.html)).

```
Device# show ip sla statistics 15011

        Latest RTT: 1 milliseconds
Latest operation start time: 15:37:35.443 EDT Mon Jun 16 2008
Latest operation return code: OK
```

This example is for `path-jitter 10.222.1.100 source-ip 10.222.3.100 num-packets 20` / `frequency 30`; for 20 probes it gives "Number of RTT: 20", "Number of jitter: 2", "Jitter Min/Avg/Max: 2/2/2 ms" and "RTT Min/Avg/Max: 1/1/3 ms". In this document's **inference**, path-jitter's jitter is the absolute difference of consecutive RTTs |RTT_i − RTT_{i−1}|, and samples with a difference of 0 are not counted (only the two transitions 1->3 and 3->1 are counted, as 2 ms). This differs from icmp-jitter, which does count a difference of 0 (Min 0, N−1 samples). The grounds for using Echo Request/Reply are three: the statement "uses ICMP echoes", the restriction that the destination's processing time cannot be compensated, and the fact that the payload-dependent `request-data-size` is provided (**inference**). The definition of "Discarded Samples", the discovery method, the use of Identifier/Sequence, how the hop table is handled when the path changes, and whether `timeout` applies per probe or per hop are not documented. The 2022 edition of the TC-MIB adds `pathJitter(27)` with the note "The 'pathJitter' time delay operation is a heuristic measurement", but its REVISION clause was not updated and there are no statistics tables ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my), [OBS-TC](https://mibs.observium.org/mib/CISCO-RTTMON-TC-MIB/)).

## Configuration parameters center on the defaults 60 s / 5000 ms / 5000 ms / 28 bytes, and are bound twice, by the CLI ranges and the MIB ranges

Configuring an operation is forced into this order: reserve an operation number with `ip sla operation-number`, enter the mode with an operation type command, give each parameter, and finally start it with `ip sla schedule`. The Command Reference specifies "IP SLAs allows a maximum of 2000 operations. Debugging is supported only on the first 32 operation numbers", "After you schedule an operation, you cannot modify the configuration of the operation. To modify the configuration of the operation after it is scheduled, you must first delete the IP SLAs operation (using the no ip sla command) and then reconfigure", and "If operation 99 already exists and has not been scheduled, the command line interface will enter IP SLA configuration mode for operation 99. If the operation already exists and has been scheduled, this command will fail", and for the operation type "You must configure the type of IP SLAs operation ... before you can configure any of the other parameters of the operation. To change the operation type of an existing IP SLAs operation, you must first delete the IP SLAs operation" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). On the MIB side, the operation number is `rttMonCtrlAdminIndex` `Integer32 (1..2147483647)`, and the CLI's limit of 2000 is exposed as `rttMonApplNumCtrlAdminEntry` ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

Several notes matter for an implementation. The recommended `timeout` is "based on the sum of both the maximum round-trip time (RTT) value for the packets and the processing time of the IP SLAs operation" ([CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)); `threshold` applies to the average jitter for UDP jitter, and "For all other IP SLAs operations, the threshold (IP SLA) command sets the upper threshold value for the round-trip time (RTT) measurement. IP SLAs will calculate the number of times the average jitter or RTT measurement exceeds the specified threshold value", so for the four ICMP operations it is an upper limit on RTT ([CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)). That the icmp-jitter output of a real device (**secondary source**) has "Number Of RTT Over Threshold: 0 (0%)" is consistent with this reading ([FRR](https://fastreroute.com/cisco-ip-sla-ios-xe/)). For `tos` it says "When the type of service is defined for an operation, the IP SLAs Responder will reflect the ToS value it receives", but ICMP has no Responder, so it depends on the behavior of the destination's stack ([CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)). The distribution of `history distributions-of-statistics-kept`, in the example "5 distributions x 10 ms interval", is "the first distribution will contain statistics from 0 to 9 ms, the second ... 10 to 19 ms, ... and the fifth distribution will contain statistics from 40 ms to infinity", and the MIB adds "the value of rttMonStatisticsAdminDistInterval does not apply when rttMonStatisticsAdminNumDistBuckets is one" (1 bucket = 0-infinity) ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). `history hours-of-statistics-kept` is "When the number of hours exceeds the specified value, the statistics table wraps and the oldest information is replaced by newer information", and the MIB adds "The value of one is not advisable because the group will close and immediately be deleted before the network management station will have the opportunity to retrieve the statistics ... HTTP and Jitter probes store only two hours of data. When this object is set to the value of zero all rttMonStatsCaptureTable data capturing will be shut off" ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The difference between `history lives-kept` and `history filter` is "The no history lives-kept command disables history collection before an IP SLAs operation is attempted. The history filter command checks for history inclusion after the operation attempt is made"; to stop history, use the former ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)).

## frequency > timeout > threshold is the only ordering rule; an overlapping run is busy, and a late reply is discarded as a sequence error

Cisco imposes one rule on non-jitter operations: "Consider the following guidelines before configuring the frequency (IP SLA), timeout (IP SLA), and threshold (IP SLA) commands. For the IP SLAs UDP jitter operation, the following guidelines are recommended: (frequency seconds) > ((timeout milliseconds) + N) ... (timeout milliseconds) > (threshold milliseconds) ... For all other IP SLAs operations, the following configuration guideline is recommended: (frequency seconds) > (timeout milliseconds) > (threshold milliseconds)" (N = num-packets x interval), and the same text is repeated in each of the frequency, timeout and threshold entries ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html), [CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)). Of this, two points are enforced: "The value specified for the timeout (IP SLA) command cannot be greater than the value specified for the frequency (IP SLA) command" and "The value specified for this command [threshold] must not exceed the value specified for the timeout command" ([CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)). The MIB writes the same constraint in both directions: `rttMonCtrlAdminFrequency` is "This object cannot be set to a value which would be a shorter duration than rttMonCtrlAdminTimeout", and `rttMonCtrlAdminTimeout` is "The value of this object cannot be set to a value which would specify a duration exceeding rttMonCtrlAdminFrequency" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). A frequency of 0 is explicitly "Value 0 is not valid for frequency" in ComplianceRev23, and only the DHCP operation has the additional lower bound "the minimum allowed value for this object is 10 seconds" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The CLI's lower bound for frequency is not given officially; only a secondary source says it "can range from 1 to 604800 (one week)" ([IPCISCO](https://ipcisco.com/lesson/cisco-ip-sla-and-configuration/)). The CLI error messages on a violation are not in Cisco's documents.

How an overlapping run is handled is settled by the busy counter: "If an individual IP SLAs operation takes longer to execute than the specified frequency value, a statistics counter called "busy" is incremented rather than immediately repeating the operation" ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)); in the MIB, "it may happen that the next RTT operation is blocked by a RTT operation which has not yet completed. In this case, the value of a counter (rttMonStatsCollectBusies) in rttMonStatsCaptureTable is incremented in lieu of initiating a RTT operation, and the next attempt will occur at the next rttMonCtrlAdminFrequency expiration", and `rttMonStatsCollectBusies` says "When the RttMonRttType is 'pathEcho' this can occur for both connection oriented protocols and connectionless protocols. When the RttMonRttType is 'echo' this can only occur for connection oriented protocols such as SNA", suggesting that busy does not occur for ICMP echo ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). For the path operations there is the guideline "When the rttMonCtrlAdminRttType object is defined to be 'pathEcho' or 'pathJitter', setting this value to a small value for your network size may cause an operation attempt (or multiple attempts) to be started before the previous operation has finished ... the suggested value for this object is greater than rttMonCtrlAdminTimeout times the maximum number of expected hops to the target" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The return code `busy(5)` is "the operation did not occur because a previous operation is still outstanding" ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my)).

A timeout is defined as `timeout(4)` "an operation timed out; no completion time recorded", and `rttMonStatsCollectTimeouts` as "The number of occasions when a RTT operation was not completed before a timeout occurred, i.e. rttMonCtrlAdminTimeout was exceeded. Since the RTT operation was never completed, the completion time of these operations are not accumulated, nor do they increment rttMonStatsCaptureCompletions"; a reply that arrives after the timeout is counted as a sequence error, as described above ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). In this document's **inference**, since timeout <= frequency x 1000 is enforced at configuration time, icmp-echo never has two unanswered requests at once, and there is no room to attribute a late reply to the next cycle. threshold is a classifier for statistics: it only produces `overThreshold(3)` "a valid completion was received but the completion time exceeded a threshold value" and `rttMonStatsCaptureOverThresholds` "successfully completed, but in excess of rttMonCtrlAdminThreshold. This number is a subset of the accumulation of all rttMonStatsCaptureCompletions. The operation time of these completed operations will be accumulated", and no trap is sent unless `ip sla reaction-configuration ... react rtt` is configured separately ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my), [CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)).

## Schedules default to life 3600 s, start-time pending and ageout 0, and the states converge on three: pending / inactive / active

### Semantics of `ip sla schedule`

The syntax is `ip sla schedule operation-number [life {forever | seconds}] [start-time {hh:mm[:ss] [month day | day month] | pending | now | after hh:mm:ss | random milliseconds}] [ageout seconds] [recurring]`, and `no ip sla schedule operation-number` is "To stop the operation and place it in the default state (pending)". The default is "The operation is placed in a pending state (that is, the operation is enabled but not actively collecting information)", and `ip sla schedule` has no `frequency` keyword (it exists only in `ip sla group schedule`) ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)).

| Keyword | Meaning (as described in the Command Reference) | Default / range | MIB |
|---|---|---|---|
| `life forever` | "Schedules the operation to run indefinitely" | - | `rttMonScheduleAdminRttLife` = 2147483647 ("the rttMonCtrlOperRttLife object will not decrement") |
| `life seconds` | "Number of seconds the operation actively collects information" | 3600 s; MIB 0..2147483647 | `rttMonScheduleAdminRttLife` DEFVAL 3600 |
| `start-time hh:mm[:ss] [month day \| day month]` | Absolute time in 24-hour notation. "The current day is implied unless you specify a month and day"; the month is the English name or its first three letters, day is 1-31 | - | `rttMonScheduleAdminRttStartTime` (TimeTicks, a future sysUpTime); in the 2016 edition `rttMonScheduleAdminStartType` specific(5) |
| `start-time pending` | "No information is collected. This is the default value" | Default | StartType pending(1); a special value of RttStartTime in the past |
| `start-time now` | "the operation should start immediately" | - | RttStartTime = 1 (special value) / StartType now(2) |
| `start-time after hh:mm:ss` | Starts hh hours mm minutes ss seconds after entry | - | StartType after(4) |
| `start-time random milliseconds` | "Adds a random number of milliseconds (between 0 and the specified value) to the current time ... The value provided for the random start time applies only to the first time the operation runs after which normal frequency rules apply" | 0-10000 ms (15.3(1)T) | StartType random(3) + `rttMonScheduleAdminStartDelay` (500..10000) ms DEFVAL 500 |
| `ageout seconds` | "Number of seconds to keep the operation in memory when it is not actively collecting information" | 0 (never ages out); MIB 0..2073600 | `rttMonScheduleAdminConceptRowAgeoutV2` DEFVAL 0 (the older `...ConceptRowAgeout` has DEFVAL 3600, deprecated) |
| `recurring` | "the operation will start automatically at the specified time and for the specified duration every day" | off | `rttMonScheduleAdminRttRecurring` DEFVAL false |

Sources: [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my), [TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my).

The Command Reference defines the ageout timeline with a diagram: "W----------------------X----------------------Y----------------------Z where: W is the time the operation was configured with the ip sla global configuration command. X is the start time or start of life of the operation (that is, when the operation became "active"). Y is the end of life as configured with the ip sla schedule global configuration command (life seconds have counted down to zero). Z is the age out of the operation. Age out starts counting down at W and Y, is suspended between X and Y, and is reset to its configured size at Y. The operation to can age out before it executes (that is, Z can occur before X). To ensure that this does not happen, configure the difference between the operation's configuration time and start time (X and W) to be less than the age-out seconds". When ageout is reached, "all configuration information for the operation is removed (that is, the configuration information is no longer in the running configuration in RAM)", and the example is `ip sla schedule 25 life 43200 start-time 15:00 apr 5 ageout 43200` ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). The MIB adds "When this conceptual Rtt control row enters an 'active' state, this timer will be reset and suspended. When this conceptual RTT control row enters a state other than 'active', the timer will be restarted. NOTE: When a conceptual Rtt control row ages out, the agent needs to remove the associated entries in the rttMonReactTriggerAdminTable and rttMonReactTriggerOperTable" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

The restrictions on recurring are "The recurring keyword is supported only for scheduling single IP SLAs operations. ... The life value for a recurring IP SLAs operation should be less than one day. The ageout value for a recurring operation must be "never" (which is specified with the value 0), or the sum of the life and ageout values must be more than one day", with the example `ip sla schedule 15 start-time 01:30:00 recurring` ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). The MIB's `rttMonScheduleAdminRttRecurring` "cannot be set to true (a) if rttMonScheduleAdminRttLife object has value greater or equal to 86400 seconds. (b) if sum of values of rttMonScheduleAdminRttLife and rttMonScheduleAdminConceptRowAgeout is less or equal to 86400 seconds"; read literally, (b) rejects ageout 0, which conflicts with the CLI rule ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). Changes after scheduling are not allowed ("After you schedule the operation with the ip sla schedule command, you cannot change the configuration of the operation"), and the MIB breaks this down: "Objects in the rttMonReactAdminTable can be modified as needed ... Objects in the rttMonScheduleAdminTable can be modified only when this object [rttMonCtrlAdminStatus] has the value of 'notInService' ... Once this object is in 'active' status, it cannot be set to 'notInService' while the rttMonCtrlOperState is in 'active' state" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). Memory is allocated at scheduling time: "The total RAM required to hold the history and statistics tables is allocated at the time of scheduling the IP SLAs operation" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). A pending operation can also be started by a trigger: "you can define the conditions under which the operation makes the transition from pending to active with the ip sla reaction-trigger and ip sla reaction-configuration global configuration commands. When the operation is in an active state, it immediately begins collecting information" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)).

### `ip sla group schedule` (multioperation scheduler)

The syntax is `ip sla group schedule group-id {operation-ids | add operation-ids | delete operation-ids | reschedule} {schedule-period seconds | schedule-together} [ageout seconds] [frequency [seconds | range random-frequency-range]] [life {forever | seconds}] [start-time {hh:mm[:ss] [month day | day month] | pending | now | after hh:mm:ss | random milliseconds}]`, and `no ip sla group schedule group-id` is "To cause all the IP SLAs operations belonging to a multioperation schedule to become inactive" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)).

| Argument | Meaning | Default / range |
|---|---|---|
| `group-id` | Group number | 0-65535 |
| `operation-ids` | "up to 125 characters", ranges with a hyphen, separated by commas (e.g. `2, 3, 4, 9, 20`, `10-20, 30-35, 60-70`). A single ID is also allowed from 15.1(1)T / 15.2(4)T | - |
| `add` / `delete` / `reschedule` | Adds to / deletes from an existing group, recalculates the start times | 12.4(6)T |
| `schedule-period seconds` | "the amount of time (in seconds) for which the group of IP SLAs operations is scheduled" | 1-604800 |
| `schedule-together` | Starts all operations at the same time | 15.3(2)S |
| `frequency seconds` | "The frequency of all operations belonging to the multioperation schedule is overridden and set to the specified frequency" | 1-604800; the default equals schedule-period |
| `frequency range a-b` | Random scheduler. Randomizes the restart interval uniformly within the range | Disabled |
| `life` / `ageout` / `start-time` | Same as for a single schedule | life 3600, ageout 0; without start-time, "no information is collected until the start-time is configured or a trigger occurs" |

Sources: [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html).

The distribution algorithm is "IP SLAs calculates how many operations it should start in each 1-second interval by dividing the number of operations by the schedule period". In the configuration guide's examples: 10 operations over 20 seconds gives 2-second intervals (0, 2, ..., 18 s); with schedule-period 20 s < frequency 30 s, 19-29 s stays empty; with schedule-period 20 s > frequency 10 s, the second period overlaps operations 6-10 of the first period, "Not recommended due to inefficient scheduling"; 10 operations over 4 s gives 2.5, so first 3 operations per second with the rest placed at the end; the minimum interval is 1 second ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html), [CG-MS-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_multi_scheduler.html)). The rules of the random scheduler are "The starting value of the frequency range should be greater than the timeout values of all the operations", "The starting value of the frequency range should be greater than the schedule period", "The minimum time interval between the start of each operation in a multioperation schedule is 100 milliseconds (0.1 seconds). If the random scheduler option is disabled, the minimum time interval is 1 second", "Only one operation can be scheduled to begin at any given time. If the random scheduler option is disabled, multiple operations can begin at the same time", "The first operation will always begin at 0 milliseconds of the schedule period", and "The order in which each operation in a multioperation schedule begins is random" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). For additions and deletions, "If two or more operations are added after the multioperation schedule has started, then the start times of the newly added operations will be uniformly distributed based on a time interval that was calculated prior to the addition" and "If an active operation is deleted, then the operation will stop collecting information and become inactive"; the skip rule is "this functionality skips those IP SLAs operations that are already running or those that are not configured and hence do not exist"; and after a reboot it "schedules the operations in the same order as was done before the reboot" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). The restrictions are "The frequency of all operations scheduled in a multioperation group must be the same", "Do not use the no ip sla group schedule and ip sla group schedule commands consecutively in a configuration file", and, from 15.1(4)M, "A random scheduler will not schedule an IP SLAs probe for which enhanced-history is configured. A fixed frequency multioperation scheduler will not schedule an IP SLAs probe for which enhanced history is configured if the enhanced-history interval is not a multiple of the scheduler frequency" ([CG-ECHO-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_icmp_echo.html), [CG-MS-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_multi_scheduler.html), [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). `show ip sla group schedule` displays "Group Entry Number: 1 / Probes to be scheduled: 3,4,6-10 / Total number of probes: 7 / Schedule period: 20 / Group operation frequency: Equals schedule period / Status of entry (SNMP RowStatus): Active / Next Scheduled Start Time: Start Time already passed / Life (seconds): 3600 / Entry Ageout (seconds): never", and `show ip sla configuration` shows "Group Scheduled: TRUE" ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html), [CG-MS-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_multi_scheduler.html)). In this document's **inference**, the start offset of the k-th operation (k = 0..N−1) is floor(k x period / N) seconds (when N <= period); when N > period, ceil(N / period) operations per 1-second slot; and the group's frequency overrides the members' own frequencies.

### Operation state machine (rttMonCtrlOperState)

The MIB's `rttMonCtrlOperState` has seven values, but the real states are three, pending, inactive and active; the rest are transition commands.

| Value | Kind | MIB definition (summary) |
|---|---|---|
| reset(1) | Command | "reset this entry, transition to 'pending'". Discards the statistics and history tables and resets their indexes to 1, creates one new statistics row if NumHourGroups != 0, resets `rttMonCtrlOperRttLife` to `rttMonScheduleAdminRttLife`, sets NumRtts to 0, and sets each of the Timeout/OverThreshold/ConnectionLost Occurred flags to false ("resolution notifications will not occur"). If the trigger state is active, goes to pending. "all open connections must be maintained" |
| orderlyStop(2) | Command | "shutdown this entry at the end of the next RTT operation attempt, transition to 'inactive'" |
| immediateStop(3) | Command | "shutdown this entry immediately (if possible), transition to 'inactive'" |
| pending(4) | State (not settable) | "waiting for further control either via the rttMonScheduleAdminTable or the rttMonReactAdminTable/rttMonReactTriggerAdminTable". Reached by reset, or by creating the row with a special value of RttStartTime (a time in the past) |
| inactive(5) | State (not settable) | "waiting for further control via the rttMonScheduleAdminTable". Reached by orderlyStop / immediateStop, or when RttLife reaches 0. On the transition, "all statistics and history collection information table entries will be closed and kept", the Occurred flags are false, and "all open connections are to be closed and cleanup" |
| active(6) | State (not settable) | "currently active" |
| restart(7) | Command | "only settable when the state is active. It clears the data of this entry and remain on active state" (the basis of the CLI `ip sla restart`) |

Sources: [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my).

The transition table (A = pending, B = inactive, C = active) is stated explicitly in the MIB. Setting OperState to reset: A->A, B->inconsistentValue, C->A. orderlyStop / immediateStop: A/B/C->B. An event that makes the trigger state active: A->C, B->B, C->C (RttLife is not reloaded). AdminStatus->active with RttStartTime = 1: A->C, B->C (from C, it must first be made inactive/pending). AdminStatus->active with RttStartTime in the past (!= 1): A->A, B->A. AdminStatus->notInService: A->A, B->B (not possible from C; force OperState to inactive/pending first). AdminStatus->destroy: every state->B. RttStartTime arrives with AdminStatus active: every state->C (from C, RttLife is not updated). RowAgeout expires: every state->B. RttLife reaches 0: C->B. The notes are "(1) rttMonCtrlOperState must have transitioned to 'inactive' or 'pending' before the rttMonCtrlAdminStatus can transition to 'active'. (2) rttMonCtrlAdminStatus cannot transition to 'notInService' unless rttMonCtrlOperState has been previously forced to 'inactive' or 'pending'. (3) when this happens the rttMonCtrlOperRttLife will not be updated with the rttMonCtrlAdminRttLife" and "this object can not be part of a multi-bound PDU" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The effect on the statistics table is "If the activity for a conceptual RTT control row ceases because the rttMonCtrlOperState object transitions to 'inactive', the corresponding current hourly group in this table is 'frozen', and a new hourly group is created when activity is resumed. If the activity ... ceases because the rttMonCtrlOperState object transitions to 'pending' this whole table will be cleared and reset to its initial state", and for the history table "A new life will be created when rttMonCtrlOperState transitions 'active'" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

The documents disagree on how they describe the state after the life expires. The MIB's `rttMonCtrlOperRttLife` says "decremented every second, until it reaches zero. When the value of this object is zero RTT operations for this row are suspended. ... When this object reaches zero the agent needs to transition the rttMonCtrlOperState to 'inactive'", but the CLI's `history lives-kept` says "When an operation makes a transition from a pending to active state, a life starts. When the life of an operation ends, the operation makes a transition from an active to pending state" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my), [CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)). The second special value of the MIB's `rttMonScheduleAdminRttStartTime` (a value earlier than now) is specified as "when the rttMonCtrlOperRttLife counts down to zero (and not when set to zero), this special value causes this conceptual Rtt control row to retransition the rttMonCtrlOperState object into 'pending' state", and the two are reconciled by this special value (**inference**) ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). Which one is displayed has not been confirmed on a real device.

The state as seen from the CLI appears in `show ip sla configuration` as "Next Scheduled Start Time: Start Time already passed | Pending trigger", "Status of entry (SNMP RowStatus): Active | notInService", "Life (seconds): 3600 / Entry Ageout (seconds): never" (older format "Life/Entry Ageout (seconds): Forever/never"), "Recurring (Starting Everyday): FALSE", "Group Scheduled : FALSE", "Randomly Scheduled : FALSE" and "Operation frequency (seconds): 60 (not considered if randomly scheduled)"; in `show ip sla statistics` as "Operational state of entry: Active", "Operation time to live: Forever" (or "2965 sec") and "Last time this entry was reset: Never"; in the older engine as "Current Seconds Left in Life: 3511", "Number of Operations Attempted: 2" and "Number of Octets in use by this Entry: 1332"; in `show ip sla summary` as "Codes: * active, ^ inactive, ~ pending"; and in `show ip sla application` as "Number of Entries configured / active Entries / pending Entries / inactive Entries" ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)). `ip sla restart operation-number` is "To restart an operation, the operation should be in an active state" and has no `no` form ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)); on a real device (**secondary source**) Number of successes goes back to 0 and Latest operation start time is updated, while the other configuration and operational parameters are kept ([IPWITHEASE](https://ipwithease.com/how-to-restart-or-clear-counters-of-ip-sla-statistics/)). `ip sla reset` restarts the whole engine: it "stops all IP SLAs operations, clears IP SLAs configuration information, and returns the IP SLAs feature to the startup condition. This command does not reread the IP SLAs configuration stored in the startup configuration", and corresponds to the MIB's `rttMonApplReset` "Any and all rows in the Overall Control Group will be immediately deleted, together with any associated rows in the Statistics Collection Group, and History Collection Group" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). This document's **inference** of the CLI<->MIB mapping is: `start-time now/absolute time/after` = AdminStatus active + RttStartTime (1 = immediately), `start-time pending` / `no ip sla schedule` = RowStatus notInService + OperState pending (statistics table cleared), reaching life 0 = OperState inactive (tables frozen and kept), `no ip sla group schedule` = inactive, `ip sla restart` = restart(7), `ip sla reset` = rttMonApplReset.

The "Latest operation return code" of `show ip sla statistics`, the Sense column of `show ip sla history`, `rttMonLatestRttOperSense`, `rttMonHistoryCollectionSense`, and the value object tracking reads are all the TC-MIB's `RttResponseSense` ([TC](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-TC-MIB.my)).

The strings of `show ip sla statistics` / `show ip sla history interval` are "OK / Over Threshold / Timeout / Unknown / Internal Error", and `show ip sla summary` shows ReturnCodes such as "OK" and "NoConnection" ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)). In `show track`, "OK", "over threshold" and "Unknown" are observed ([EOT-CR-S](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipapp/command/iap-cr-book/iap-s3.html)). For codes irrelevant to ICMP, the MIB says `rttMonStatsCollectNumDisconnects` "For connectionless protocols this has no meaning, and will consequently remain 0", `rttMonStatsCollectNoConnections` "This cannot occur for connectionless protocols", and `rttMonStatsCollectDrops` "some necessary internal resource (for example memory, or SNA subsystem) was not available, or the operation completion could not be recognized" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

The accounting of successes, failures and threshold violations is expressed differently in the MIB and the CLI. In the MIB, `rttMonStatsCaptureCompletions` = "The number of RTT operations that have completed without an error and without timing out", `rttMonStatsCaptureOverThresholds` is a **subset** of Completions whose completion times are also accumulated, Timeouts / Busies / Drops / SequenceErrors / VerifyErrors are all "the completion time of these operations are not accumulated, nor do they increment rttMonStatsCaptureCompletions", and `rttMonStatsTotalsInitiations` "includes all RTT operations which succeed or fail for whatever reason" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). In the history, "If the RTT operation fails (rttMonHistoryCollectionSense is any value other than ok), this has a value of 0": the completion time is 0 for anything other than ok ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The CLI's `show ip sla statistics aggregated ... details`, on the other hand, lists over threshold as one of the causes of failure: "Number of successes: 0 / Number of failures: 23 / Failed Operations due to over threshold: 0 / Failed Operations due to Disconnect/TimeOut/Busy/No Connection: 0/23/0/0 / Failed Operations due to Internal/Sequence/Verify Error: 0/0/0" ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)). A real IOS 12.4-generation device (**secondary source**, `timeout 500` / `threshold 20` / `frequency 10` with an RTT of 36 ms) showed "Latest operation return code: Over threshold / Number of successes: 0 / Number of failures: 6", counting over threshold among the CLI's failures ([NETEXPERT](http://netexpert.blogspot.com/2009/02/ip-sal-timeout-or-threshold.html)). In the enhanced history the OvrTh column is placed next to Comps and described as "Operations completed over thresholds", which matches the MIB's "subset of completions" model ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)). As an **inference** of this document, an accounting that satisfies both takes the MIB-style counters as authoritative (Completions including over threshold, with RTT accumulated; OverThresholds, Timeouts, Busies, Drops, SequenceErrors, VerifyErrors, Initiations), and defines the CLI's Number of successes = Completions − OverThresholds (return code ok only), Number of failures = Initiations − successes, "Failed Operations due to over threshold" = OverThresholds, and "Number Of RTT" and RTT Min/Avg/Max = all timed completions including over threshold; but whether the current IOS XE 17.x CLI behaves this way cannot be confirmed from Cisco's documents.

## Statistics are kept in three layers, "hourly aggregation", "snapshot history" and "enhanced history", and each show command reflects one of them

The overview guide defines the three kinds as "Aggregated statistics--By default, IP SLAs maintains two hours of aggregated statistics for each operation. ... Operation snapshot history--IP SLAs maintains a snapshot of data for each operation instance that matches a configurable filter, such as all, over threshold, or failures. The entire set of data is available and no aggregation takes place. Distribution statistics--IP SLAs maintains a frequency distribution over configurable intervals. ... By default, the history for an IP SLAs operation is not collected. ... History buckets do not wrap" ([CG-OV-15MT](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_overview-0.html)).

### Hourly aggregated statistics (hourly group and distribution bucket)

The MIB's `rttMonStatsCaptureTable` sets the structure: "A rolling accumulated history of this information is maintained in a series of hourly 'group(s)'. Each 'group' contains a series of 'path(s)', each 'path' contains a series of 'hop(s)', each 'hop' contains a series of 'statistics distribution bucket(s)'. Each conceptual statistics row has a current hourly group, into which RTT results are accumulated. At the end of each hour a new hourly group is created which then becomes current. The counters and accumulators in the new group are initialized to zero. The previous group(s) is kept in the table until the table contains rttMonStatisticsAdminNumHourGroups groups ... at this point, the oldest group is discarded and is replaced by the newly created one. The hourly group is uniquely identified by the rttMonStatsCaptureStartTimeIndex object", and adds "When the RttMonRttType is 'pathEcho', the path exploration RTT requests' statistics will not be accumulated in this table" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The accumulators of each bucket are Completions, OverThresholds, `SumCompletionTime` (Gauge32 ms), `SumCompletionTime2Low/High` (the 64 bits of the sum of squares split into two 32-bit halves, "the number 4294967296 would have all Low order bits as '0' and the rightmost High order bit will be 1"), `CompletionTimeMax` and `CompletionTimeMin`, and the distribution index is "all values that fall above the last interval will be placed into the last interval" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The error counts are in `rttMonStatsCollectTable` ("exact same behavior as the rttMonStatsCaptureTable, except it does not keep statistical distribution information"), which has NumDisconnects / Timeouts / Busies / NoConnections / Drops / SequenceErrors / VerifyErrors / Address, and `rttMonStatsTotalsTable` has `ElapsedTime` "The length of time since this conceptual statistics row was created" and `Initiations` ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The CLI says "This command shows information collected over the past two hours, unless you specify a different amount of time using the history hours-of-statistics-kept command", and shows the hour group with a wall-clock time of ms precision, like `Start Time Index: 05:31:12.896 PST Wed Sep 3 2003` ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)). In this document's **inference**, the hour boundaries are every 60 minutes from the time the group was created (not on the wall clock's hour), bucket index = min(floor(t / DistInterval) + 1, NumDistBuckets), Avg = Sum / Completions, and standard deviation = sqrt(Sum² / N − (Sum / N)²). Whether the hour boundaries are realigned to the top of the hour, and whether the Start Time Index of the first group matches the start time of the operation, are undocumented.

### Snapshot history (lives / buckets / samples / filter)

The MIB defines "The history table contains a point by point rolling history of the most recent RTT operations for each conceptual RTT control row. The rolling history of this information is maintained in a series of 'live(s)', each containing a series of 'bucket(s)', each 'bucket' contains a series of 'sample(s)'. ... A bucket will contain one sample per bucket if the rttMonCtrlAdminRttType object is set to any value other than 'pathEcho'. If ... 'pathEcho', a bucket will contain one sample per hop along a path to the target (including the target)", and a sample has `SampleTime` "The time that the RTT operation was initiated" (sysUpTime), `Address`, `CompletionTime` (ms, 0 on failure), `Sense`, `ApplSpecificSense` and `SenseDescription` ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). A life is "A life is defined by the countdown (or transition) to zero by the rttMonCtrlOperRttLife object. A new life is created when the same conceptual RTT control row is restarted"; `rttMonHistoryAdminNumLives` is 0..2, DEFVAL 0 ("The value of zero will shut off all rttMonHistoryAdminTable data collection"), and `rttMonHistoryCollectionLifeIndex` is "The sequence keeps incrementing, despite older (lower) values being removed from the table" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). A bucket is "this object increments on each operation attempt. ... The sequence keeps incrementing until the number of buckets equals rttMonHistoryAdminNumBuckets, after which the most recent rttMonHistoryAdminNumBuckets buckets are retained (the index is incremented though)" (1..60, DEFVAL 15), which contradicts the CLI's "History buckets do not wrap" and "The default is 50". Every official show sample prints "Number of history Buckets kept: 15", so 15 is the reasonable default for an implementation ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my), [CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html), [CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)). The filter is `rttMonHistoryAdminFilter` "none - no history is recorded; all - the results of all completion times and failed completions are recorded; overThreshold - the results of completion times over rttMonCtrlAdminThreshold are recorded; failures - the results of failed operations (only) are recorded" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The history table is "not applicable to http and jitter probes", which agrees with icmp-jitter mode having no history commands ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The data model by this document's **inference** is history[life][bucket][sample] (life = one activation, bucket = one attempt or one path discovery, sample = one hop); the filter decides after the attempt whether to insert, and lives-kept = 0 stops collection before the attempt.

### Enhanced history (history enhanced)

`history enhanced [interval seconds] [buckets number-of-buckets]` is "Performance statistics are stored in buckets that separate the accumulated data. Each bucket consists of data accumulated over the specified time interval. When the interval expires, history statistics are gathered in a new bucket. When the specified number of buckets is reached, statistic gathering for the operation ends. By default, IP SLAs maintains two hours of aggregated statistics for each operation. Values from each operation cycle are aggregated with the previously available data within a given hour. The Enhanced History feature in IP SLAs allows for the aggregation interval to be shorter than one hour", with interval 1-3600 s (default 900), buckets 1-100 (default 100), and disabled by default ([CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)). It does not say whether "statistic gathering for the operation ends" also extends to the ordinary hourly statistics.

## Threshold reactions send one notification per rising->falling transition; the defaults are never / none, and the default thresholds for rtt are 5000 / 3000 ms

### Syntax and evaluation algorithm of `ip sla reaction-configuration`

The syntax is `ip sla reaction-configuration operation-number [react monitored-element [action-type option] [threshold-type {average [number-of-measurements] | consecutive [occurrences] | immediate | never | xofy [x-value y-value]}] [threshold-value upper-threshold lower-threshold]]` and `no ip sla reaction-configuration operation-number [react monitored-element]`, and the default is "IP SLAs proactive threshold monitoring is disabled". For multiple elements, "You can configure the ip sla reaction-configuration command multiple times to enable proactive threshold monitoring for multiple elements ... However, disabling individual monitored elements is not supported. The no ip sla reaction-configuration command disables all proactive threshold monitoring configuration for the specified IP SLAs operation"; the keywords are case-insensitive, an unsupported element returns "Invalid react option for the Probe type configured", and from 15.1(1)T shift+? lists the supported elements ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). In the MIB, `rttMonReactTable` (INDEX { rttMonCtrlAdminIndex, rttMonReactConfigIndex }) represents one reaction per row, "Each Probe can have multiple reactions and hence there can be multiple rows for a particular probe", and `rttMonReactStatus` is "Only CreateAndGo and destroy operations are permitted on the row ... In order for this object to become active rttMonReactVar must be defined. All other objects assume the default value" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

| threshold-type | CLI definition | Default and range | Set / clear rules of MIB `rttMonReactThresholdType` |
|---|---|---|---|
| `never` | "Do not calculate threshold violations. This is the default threshold type" | Default | never(1) "rttMonReactOccurred is never set" |
| `immediate` | "When a threshold violation for the monitored element is met, immediately perform the action" | - | immediate(2): true when the value violates the threshold; "Conversely, rttMonReactOccurred is set to 'false' when the parameter ... is below the threshold limits" |
| `consecutive [occurrences]` | "When a threshold violation ... is met consecutively for a specified number of times". The value is "Threshold Count" in `show ip sla reaction-configuration` | 5, 1-16 | consecutive(3): "violates the threshold for configured consecutive times ... Conversely ... below the threshold limits for the same number of consecutive operations" |
| `xofy [x-value y-value]` | "met x number of times within the last y number of measurements". x = Threshold Count, y = Threshold Count2 | 5 5, each 1-16 | xOfy(4): "x (rttMonReactThresholdCountX) out of the last y (rttMonReacthresholdCountY) times ... violates ... Conversely ... x, out of the last y times ... below the threshold limits. NOTE: When x > y, the probe will never generate a reaction" |
| `average [number-of-measurements]` | "When the average of a specified number of measurements ... exceeds the upper threshold or ... drops below the lower threshold". Example: for rtt 5000, 6000, 6000, 5000 -> average 5667, a violation. "not available if the connectionLoss, timeout, or verifyError keyword is specified" | 5, 1-16 | average(5): "the average (rttMonReactThresholdCountX times) value ... violates the threshold condition. Conversely ... the average value ... is below the threshold limits" |

Sources: [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my). `rttMonReactThresholdCountX` (1..16, DEFVAL 5) serves as the x of xOfy, the count of consecutive and the number of samples of average; `rttMonReactThresholdCountY` (1..16, DEFVAL 5) is used only as the y of xOfy; and "If this value [ThresholdType] is changed by a management station, rttMonReactOccurred is set to false, but no reaction is generated if the prior value of rttMonReactOccurred was true" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

`action-type` has four values: `none` "No action is taken. This option is the default value", `trapOnly` "Send an SNMP logging trap when the specified violation type occurs", `triggerOnly` "Transition one or more target operation's operational state from pending to active ... specified using the ip sla reaction-trigger command", and `trapAndTrigger`; "If the threshold-type never keywords are defined, the action-type keyword is disabled", and in the MIB it is `rttMonReactActionType` none(1)/trapOnly(2)/triggerOnly(3)/trapAndTrigger(4) DEFVAL none ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html), [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). `threshold-value upper-threshold lower-threshold` corresponds to the MIB's `rttMonReactThresholdRising` "If the value ... rises above this limit and if the condition specified in rttMonReactThresholdType are satisfied, a trap is generated" and `rttMonReactThresholdFalling` "If the value ... falls below this limit ..." (both Integer32 0..2147483647, "not applicable if the rttMonReactVar is 'timeout', 'connectionLoss' or 'verifyError' ... default value ... will be 0") ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)).

Notifications occur only on transitions. The configuration guide says "Notifications are not issued for every occurrence of a threshold violation. ... An event is sent and a notification is issued when the rising threshold is exceeded for the first time. Subsequent threshold-exceeded notifications are issued only after the monitored value falls below the falling threshold before exceeding the rising threshold again", and gives as the steps of its figure "1 An event is sent and a threshold-exceeded notification is issued when the rising threshold is exceeded for the first time. 2 Consecutive over-rising threshold violations occur without issuing additional notifications. 3 The monitored value goes below the falling threshold. 4 Another threshold-exceeded notification is issued when the rising threshold is exceeded only after the monitored value first fell below the falling threshold", with the note "A lower-threshold notification is also issued the first time that the monitored element falls below the falling threshold (3)" ([CG-THR-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_threshold_mon-0.html), [CG-THR-122SR](https://www.cisco.com/c/en/us/td/docs/ios/ipsla/configuration/guide/12_2sr/sla_12_2sr_book/sla_threshold_mon.html)). The MIB's `rttMonReactOccurred` (DEFVAL false) is "set to true when the configured threshold condition is violated ... It will be again set to 'false' if the condition reverses"; timeout / connectionLoss / verifyError directly reflect the truth value of the corresponding `rttMonCtrlOper*Occurred`; "For all other values of rttMonReactVar, if the corresponding value exceeds the configured rttMonReactThresholdRising" it becomes true, and on "fall below the configured rttMonReactThresholdFalling" false; and "When the RttMonRttType is 'pathEcho' or 'pathJitter', this object is applied only to the rttMonEchoAdminTargetAddress" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). `rttMonReactValue` (read-only) "holds the actual value that violated the configured threshold values ... timeout - connectionLoss - verifyError [for these it is] always 0" ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). The evaluation machine by this document's **inference** keeps, per reaction row, occurred (initially false), a window of the last y results, a consecutive counter and an average buffer (N results); on each completed measurement, if occurred = false it decides a "violation" (value > rising), and if true a "recovery" (value < falling), by the per-type rule (immediate: 1 result, consecutive: N in a row of the same kind, xofy: x of the last y, average: the average of the last N), and emits a rising event exactly once on false->true and a falling event exactly once on true->false. The boundary values (equality), whether the average window is sliding, whether the xofy window is reset on a transition, and whether lower <= upper is validated are not documented.

The RTT reaction of the jitter operations is evaluated only once, at the end of the operation: "Return-trip time (RTT) reactions for jitter operations are triggered only at the end of the operation and use the latest value for the return-trip time (LatestRTT). SNMP traps for RTT for jitter operations are based on the average value for the return-trip time (RTTAvg) for the whole operation only and do not include return-trip time values for individual packets sent during the operation", "For example, if the average is below the threshold, up to half of the packets can actually be above threshold but this detail is not included in the notification", and "Only syslog messages are supported for RTTAvg threshold violations" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html), [CG-THR-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_threshold_mon-0.html)).

### `ip sla reaction-trigger`

`ip sla reaction-trigger operation-number target-operation` is "define a second Cisco IOS IP Service Level Agreements (SLAs) operation to make the transition from a pending state to an active state when one of the trigger action type options are defined", with the default "No trigger combination is defined" and "Triggers are usually used for diagnostics purposes and are not intended for use during normal operation conditions"; the example `ip sla reaction-trigger 2 1` makes operation 1 go pending->active on a violation by operation 2 ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). How long it runs changed between releases: "Before Cisco IOS Release 15.2(3)T, when an IP SLA operation is triggered, the (triggered) target operation starts and continues to run independently and without knowledge of the condition of the triggering operation. The target operation continues to run until its life expires ... The target operation must finish its life before it can be triggered again. In Cisco IOS Release 15.2(3) and later releases, the (triggered) target operation runs until the condition-cleared event. Afetr [sic] which the target operation gracefully stops and the state of the target operation changes from Active to Pending so it can be triggered again" ([CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)). The MIB's `rttMonReactTriggerAdminTable` is "If the conceptual RTT control row is undefined, and a trigger occurs, no action will take place. If the conceptual RTT control row is scheduled to start at a later time, triggering that row will have no effect. If the conceptual RTT control row is currently active, triggering that row will have no effect on that row, but the rttMonReactTriggerOperState object will transition to 'active'. An entry in this table can only be triggered when it is not currently in a triggered state", and `rttMonReactTriggerOperState` is active(1)/pending(2) ([MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)). `show ip sla reaction-trigger 1` prints "Reaction Table / Entry Number: 1 / Target Entry Number: 2 / Status of Entry (SNMP RowStatus): active / Operational State: pending" ([CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)).

## track ip sla reads only OK as Up for state, and OverThreshold as Up too for reachability

`track object-number ip sla operation-number [state | reachability]` (replaced `track rtr` in 12.4(20)T, object-number 1-1000, default "IP SLAs tracking is disabled") is defined as "Every IP SLAs operation maintains an operation return-code value. This return code is interpreted by the tracking process. The return code may return OK, OverThreshold, and several other return codes. Different operations may have different return-code values, so only values common to all operation types are used. Two aspects of an IP SLAs operation can be tracked: state and reachability. The difference between these aspects relates to the acceptance of the OverThreshold return code" ([EOT-CR-T](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipapp/command/iap-cr-book/iap-t1.html)).

| Tracking type | Return code -> state |
|---|---|
| `state` | OK -> Up; everything else -> Down |
| `reachability` | OK or OverThreshold -> Up; everything else -> Down |

Sources: [EOT-CR-T](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipapp/command/iap-cr-book/iap-t1.html); the same table is in [EOT-CG-XE17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_iap-eot-xe.html) and [EOT-CG-C9350](https://www.cisco.com/c/en/us/td/docs/switches/lan/c9000/lyr3-fwd/enhanced-object-tracking/enhanced-object-tracking-configuration-guide/ip-slas-object-tracking.html) (object-number 1-500, operation-number 1-2147483647).

Tracking is poll-based: the default of `track timer {application | interface | ip {route | sla} | ipv6 route | list | stub-object} {seconds | msec milliseconds}` for IP SLA is 5 seconds (seconds 1-3000, msec 500-5000; `sla` from 12.2(33)SRE, `msec` from 15.0(1)M), and `show track timer` shows "ip sla 5 expired" ([EOT-CR-T](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipapp/command/iap-cr-book/iap-t1.html), [EOT-CR-S](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipapp/command/iap-cr-book/iap-s3.html)). `delay {up seconds [down seconds] | [up seconds] down seconds}` is "a period of time to delay communicating state changes of a tracked object", 0-180 seconds, default 0 (the Catalyst 9500 17.3 guide says 1-180) ([EOT-CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipapp/command/iap-cr-book/iap-a1.html), [EOT-CG-9500](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9500/software/release/17-3/configuration_guide/ip/b_173_ip_9500_cg/configuring_enhanced___object_tracking.html)). The key point of these two examples is that the same "over threshold" is Up for reachability and Down for state. The technical note on static route failover shows `track 8 ip sla 1 reachability` / `ip sla 1` / `icmp-echo 10.0.12.2 source-ip 10.0.12.1` / `ip sla schedule 1 life forever start-time now` / `ip route 0.0.0.0 0.0.0.0 10.0.12.2 track 8` / `ip route 0.0.0.0 0.0.0.0 10.0.13.2 10`, and `show track` shows "Track 8 / IP SLA 1 reachability / Reachability is Up / 7 changes, last change 00:00:17 / Latest operation return code: OK / Latest RTT (millisecs) 1 / Tracked by: / Static IP Routing 0"; the defaults it relies on are Threshold 5000 / Timeout 5000 / Frequency 60 ([TECHNOTE](https://www.cisco.com/c/en/us/support/docs/ip/ip-routing/200785-ISP-Failover-with-default-routes-using-I.html)). A state change is logged as `%TRACK-6-STATE: 100 ip sla 100 reachability Up -> Down` (**secondary source**) ([IPSPACE](https://blog.ipspace.net/kb/internet/mh_soho/40-monitor/)). In this document's **inference**, the tracker reads the return code of the most recently completed operation, and with the icmp-echo defaults it does not go Down until the next probe times out, so the failover delay is about frequency + timeout + delay down (+ up to one polling interval); for path-echo only the result of the destination hop affects the return code. Whether IP SLA pushes results to the tracker (`react-alert` registration) or it is polling only is undocumented.

EEM subscribes to reactions with `event [tag event-tag] ipsla {group-name name [operation-id operation-id-value] | operation-id operation-id-value [group-name name]} [dest-ip-address ip-address] [reaction-type type] [maxrun maxruntime-number]` (12.4(22)T / 12.2(33)SRE). "An EEM event is published when an IP SLAs reaction is triggered. Either the group-name or the operation-id must be specified"; reaction-type is the fixed set connectionLoss, icpif, jitterAvg, jitterDSAvg, jitterSDAvg, maxOfNegativeDS, maxOfNegativeSD, maxOfPositiveDS, maxOfPositiveSD, mos, packetLateArrival, packetLossDS, packetLossSD, packetMIA, packetOutOfSequence, rtt, timeout, verifyError; and the default is "No events are published when IP SLAs operations are triggered" ([EEM-CR](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/eem/command/eem-cr-book/eem-cr-e1.html)). `event_reqinfo` for Tcl's `event_register_ipsla` returns "group_name / operation_id / condition (cleared / occurred) / reaction_type / dest_ip_addr / threshold_rising / threshold_falling / measured_threshold_value / threshold_count1 / threshold count2" ([EEM-TCL](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/syst-mgmt/b-system-management/m_eem-event-reg-tcl.html)). That condition has both occurred and cleared supports that events are emitted on both the rising and falling edges of the reaction state machine, and measured_threshold_value corresponds to `rttMonReactValue` (**inference**). There is no official table of the applet-side `$_ipsla_*` variable names; information on them is limited to the community.

## Implementation guidance: requirements derivable from Cisco's documents, and undocumented matters the implementer must decide

This section is this document's organization for an ICMP implementation on Linux; read it not as Cisco's behavior but as requirements derived from the primary sources of the previous sections (**inference**).

### Derivable requirements and validation rules

Configuration validation enforces at configuration time an operation number of 1..2147483647 (practical limit 2000), `frequency` 1..604800 s (rejecting 0), `timeout` 0..604800000 ms, `threshold` 0..60000 ms, and threshold <= timeout <= frequency x 1000; for `request-data-size` it takes the echo minimum of 28 within the type range 0..16384 (for the conflict with the CLI's "from 0", the MIB side is the safe side). It validates `tos` 0..255, `traffic-class` 0..255, `flow-label` 0..1048575, `tag` 0..16 (LongTag 0..128), `owner` 0..255, `history lives-kept` 0..2, `history buckets-kept` 1..60 (default 15), `samples-of-history-kept` 1..30, `paths-of-statistics-kept` 1..128 (default 5), `hops-of-statistics-kept` 1..30 (default 16), `history distributions-of-statistics-kept` 1..20, `history statistics-distribution-interval` 1..100 ms, `history hours-of-statistics-kept` 0..25 (default 2), `history enhanced interval` 1..3600 / `buckets` 1..100, `interval` 0..60000 ms, `life` 0..2147483647 (2147483647 = forever), `ageout` 0..2073600, `start-time random` 0..10000 ms, the reaction count 1..16 and threshold-value 0..2147483647, and for recurring, life < 86400 and (ageout = 0 or life + ageout > 86400). Changing a scheduled operation requires deleting it with `no ip sla N`, and a change of operation type is treated the same way. For the path operations, it warns if frequency > timeout x the expected number of hops does not hold.

For packets, icmp-echo / path-echo / path-jitter send ICMP Echo Request (Type 8 for IPv4, ICMPv6 Echo for IPv6) with data part = an 8-byte area for the sender's timestamp/sequence + a pattern of `request-data-size` bytes (a repetition of the default 0xABCDABCD is a candidate), making an IP packet of 36 + N bytes for IPv4. Replies are matched by Identifier/Sequence and the data part, and with `verify-data` enabled, the echoed data part and size are compared byte by byte with what was sent, and a mismatch becomes verifyError(9). A reply that arrives after the timeout, and a duplicate reply, are counted as sequenceError(8) and not attributed to the next cycle. The send time is taken just before sending and the receive time with `SO_TIMESTAMP` / `SO_TIMESTAMPNS` (a hardware timestamp if possible), to come close to Cisco's interrupt-level TS4. RTT is rounded to whole ms and stored in the statistics, the history and the MIB (µs is an extension for UDP jitter only, so it is not produced for ICMP). ICMP jitter sends `num-packets` Type 13 Timestamp Requests at `interval` ms, writes ms-since-midnight-UT in Originate, computes from the Receive / Transmit of the Reply and the receive time, with the formulas of the earlier section, RTT, SD/DS one-way delay, SD/DS jitter (count / sum / sum² / min / max for positive and negative separately), loss, late, skipped and out-of-sequence (SD / DS / both), and handles the wrap across midnight and the high-order bit. One-way delay is not counted as a sample unless time synchronization with the destination can be confirmed (matching Cisco's real-device behavior of "0 samples"). path-echo / path-jitter separate a discovery phase (the implementer chooses UDP or ICMP) from a measurement phase, assign a new path index when the sequence of hops changes, make index 1 the source-to-target path that collects errors, and decide reactions and return codes from the result of the destination hop only.

The state machine adds the four commands reset / orderlyStop / immediateStop / restart to the three states pending / inactive / active, and implements the MIB's transition table and side effects as they are (reset discards statistics and history and resets indexes to 1, inactive freezes and keeps the hour groups, pending clears the statistics table, activation starts a new life, ageout decreases only while not active and is reset on activation, and on expiry the operation is deleted along with its configuration). life is decremented every second and at 0 the operation becomes inactive (Cisco's CLI documents also say pending for the display, so decide which to show). Statistics keep `hours-of-statistics-kept` hour groups, cut every 60 minutes from the start of the operation, each group holding Completions / OverThresholds / Sum / Sum² (64 bit) / Min / Max per (path, hop, dist bucket), error counters per (path, hop), and Initiations / ElapsedTime per group. The history is lives x buckets x samples, keeping the latest N buckets (indexes increase monotonically); the filter is decided after the attempt, and lives = 0 before it. Reactions keep an occurred flag and windows per row, emit notifications only on rising / falling transitions (three paths: syslog, the varbind set of SNMP `rttMonNotificationV2`, and an external hook), and follow the per-element table of which deliveries are supported. The tracking-like feature computes `state` (Up for OK only) and `reachability` (Up for OK / OverThreshold) from the latest return code, and provides hysteresis equivalent to `delay up/down`. When aiming for MIB compatibility, provide the 1.3.6.1.4.1.9.9.42 subtree with AgentX or similar, put the two tables of the ICMP-MIB inside it, set echo(1) / pathEcho(2) / icmpjitter(16) (and pathJitter(27)) to true in rttMonApplSupportedRttTypesTable and ipIcmpEcho(2) / icmpJitterAppl(34) in SupportedProtocolsTable, and pass IPv4 targets as raw 4 octets.

## Conclusion

The four ICMP operations of Cisco IP SLA look on the surface like "automated ping", but in substance they are a measurement engine built around the data model of the RTTMON MIB. Most of the CLI's defaults, ranges and displays reduce to the DEFVALs and DESCRIPTIONs of MIB objects, and wherever the CLI documents conflict with the MIB (history buckets 50 vs 15, ageout 3600 vs 0, request size 1 vs 28), the true value lies on the MIB side or in the show output; a Linux implementation therefore gets a consistent design by settling on "the MIB is authoritative, the CLI is the display". Conversely, the layers Cisco deliberately does not publish, such as the internal format of the ICMP echo payload, the path discovery procedure, the acceptance of ICMP jitter one-way delay samples, and the CLI's success/failure accounting, are areas where compatibility cannot be claimed, and the implementation must write down its own specification for them.

As for the order of implementation, the one that best follows the layered structure of Cisco's own design is: first build, with icmp-echo, the control rows, scheduling, state machine, hourly statistics, history, return codes and reactions in line with the MIB; extend that to path-echo (adding the path/hop dimensions) and icmp-jitter (the two tables of the ICMP-MIB and per-direction statistics); and add path-jitter last as a CLI-only feature not supported by the MIB. For verifying compatibility, it is practical to use the official show samples and the secondary-source real-device output collected in this document as expected values, and to add the results confirmed on real devices to the specification for the undocumented items.
