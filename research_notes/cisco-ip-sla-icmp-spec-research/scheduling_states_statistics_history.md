## 1. `ip sla schedule` — single-operation scheduling semantics (life / start-time / ageout / recurring / modification rules)

### Takeaway
`ip sla schedule <op> [life {forever | seconds}] [start-time {hh:mm[:ss] [month day | day month] | pending | now | after hh:mm:ss | random ms}] [ageout seconds] [recurring]`; defaults: life 3600 s, start-time pending, ageout 0 (never), recurring off. Life expiry stops collection (MIB: state → inactive; CLI history docs describe active → pending), ageout removes the operation's configuration entirely, and a scheduled operation cannot be modified without `no ip sla <op>` first.

### Cited Findings
- Exact syntax (CR-I): `ip sla schedule operation-number [life {forever | seconds}] [start-time {hh : mm [: ss] [month day | day month] | pending | now | after hh : mm : ss | random milliseconds}] [ageout seconds] [recurring]` / `no ip sla schedule operation-number`. Purpose of `no` form: "To stop the operation and place it in the default state (pending)". — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- `life forever`: "(Optional) Schedules the operation to run indefinitely." `life seconds`: "(Optional) Number of seconds the operation actively collects information. The default is 3600 seconds (one hour)." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Life range/"forever" encoding in the MIB: `rttMonScheduleAdminRttLife` Integer32 (0..2147483647), UNITS seconds, DEFVAL 3600; "The value 2147483647 has a special meaning. When this object is set to 2147483647, the rttMonCtrlOperRttLife object will not decrement. And thus the life time will never end." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- `start-time` keyword semantics (CR-I): `hh:mm[:ss]` "Specifies an absolute start time using hour, minute, and (optionally) second. Use the 24-hour clock notation ... The current day is implied unless you specify a month and day."; `month` "If month is not specified, the current month is used. Use of this argument requires that a day be specified. You can specify the month by using either the full English name or the first three letters of the month."; `day` "(in the range 1 to 31) ... requires that a month be specified."; `pending` "(Optional) No information is collected. This is the default value."; `now` "Indicates that the operation should start immediately."; `after hh:mm:ss` "Indicates that the operation should start hh hours, mm minutes, and ss seconds after this command was entered."; `random milliseconds` "Adds a random number of milliseconds (between 0 and the specified value) to the current time, after which the operation will start. The range is from 0 to 10000." (random keyword added in 15.3(1)T). — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Random start-time detail: "The value provided for the random start time applies only to the first time the operation runs after which normal frequency rules apply." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- `ageout seconds`: "(Optional) Number of seconds to keep the operation in memory when it is not actively collecting information. The default is 0 seconds (never ages out)." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Ageout range in the MIB: `rttMonScheduleAdminConceptRowAgeout` Integer32 (0..2073600) seconds, "The amount of time this conceptual Rtt control row will exist when not in an 'active' rttMonCtrlOperState. When this conceptual Rtt control row enters an 'active' state, this timer will be reset and suspended. When this conceptual RTT control row enters a state other than 'active', the timer will be restarted. ... When this value is set to zero, this entry will never be aged out." MIB DEFVAL is 3600, but MIB-2016 adds `rttMonScheduleAdminConceptRowAgeoutV2` (0..2073600, DEFVAL 0) "It is the same as rttMonScheduleAdminConceptRowAgeout except DEFVAL is 0 to be consistent with CLI ageout default." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB); [MIB-2016](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)
- Ageout timeline (CR-I, verbatim): "W----------------------X----------------------Y----------------------Z where: W is the time the operation was configured with the ip sla global configuration command. X is the start time or start of life of the operation (that is, when the operation became "active"). Y is the end of life as configured with the ip sla schedule global configuration command (life seconds have counted down to zero). Z is the age out of the operation. Age out starts counting down at W and Y, is suspended between X and Y, and is reset to its configured size at Y. The operation to can age out before it executes (that is, Z can occur before X). To ensure that this does not happen, configure the difference between the operation's configuration time and start time (X and W) to be less than the age-out seconds." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- What ageout does to configuration (CR-I example text): "This operation will age out after 12 hours of inactivity, which can be before it starts or after it has finished with its life. When this operation ages out, all configuration information for the operation is removed (that is, the configuration information is no longer in the running configuration in RAM)." Example: `ip sla schedule 25 life 43200 start-time 15:00 apr 5 ageout 43200`. — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- MIB ageout side-effect: "When a conceptual Rtt control row ages out, the agent needs to remove the associated entries in the rttMonReactTriggerAdminTable and rttMonReactTriggerOperTable." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- `recurring`: "(Optional) Indicates that the operation will start automatically at the specified time and for the specified duration every day." Restrictions: "The recurring keyword is supported only for scheduling single IP SLAs operations. You cannot schedule multiple IP SLAs operations using the ip sla schedule command. The life value for a recurring IP SLAs operation should be less than one day. The ageout value for a recurring operation must be "never" (which is specified with the value 0), or the sum of the life and ageout values must be more than one day. If the recurring option is not specified, the operations are started in the existing normal scheduling mode." Example: `ip sla schedule 15 start-time 01:30:00 recurring` ("begins automatically collecting data every day at 1:30 a.m."). — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- MIB view of recurring: `rttMonScheduleAdminRttRecurring` TruthValue DEFVAL false: "When set to true, this entry will be scheduled to run automatically for the specified duration equal to the life configured, at the same time daily. This value cannot be set to true (a) if rttMonScheduleAdminRttLife object has value greater or equal to 86400 seconds. (b) if sum of values of rttMonScheduleAdminRttLife and rttMonScheduleAdminConceptRowAgeout is less or equal to 86400 seconds." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Command default: "The operation is placed in a pending state (that is, the operation is enabled but not actively collecting information)." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Modification rule: "After you schedule the operation with the ip sla schedule command, you cannot change the configuration of the operation. To change the configuration of the operation, use the no form of the ip sla global configuration command and reenter the configuration information." Also (ip sla command): "If operation 99 already exists and has not been scheduled, the command line interface will enter IP SLA configuration mode for operation 99. If the operation already exists and has been scheduled, this command will fail." and `no ip sla <n>` removes "all configuration information for an operation, including the schedule of the operation, reaction configuration, and reaction triggers". — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- MIB equivalent of the modification rule: "Most conceptual Rtt control row objects cannot be modified once this conceptual Rtt control row has been created. The objects that can change are ... Objects in the rttMonReactAdminTable can be modified as needed ... Objects in the rttMonScheduleAdminTable can be modified only when this object [rttMonCtrlAdminStatus] has the value of 'notInService'. ... Once this object is in 'active' status, it cannot be set to 'notInService' while the rttMonCtrlOperState is in 'active' state." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Pending → active via reaction triggers: "If the operation is in a pending state, you can define the conditions under which the operation makes the transition from pending to active with the ip sla reaction-trigger and ip sla reaction-configuration global configuration commands. When the operation is in an active state, it immediately begins collecting information." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Memory allocation at schedule time: "The total RAM required to hold the history and statistics tables is allocated at the time of scheduling the IP SLAs operation. This prevents router memory problems when the router gets heavily loaded and lowers the amount of overhead an IP SLAs operation causes on a router when it is active." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- End of life, MIB: `rttMonCtrlOperRttLife` "is decremented every second, until it reaches zero. When the value of this object is zero RTT operations for this row are suspended. ... When this object reaches zero the agent needs to transition the rttMonCtrlOperState to 'inactive'." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- End of life, CLI history doc (different wording): "When an operation makes a transition from a pending to active state, a life starts. When the life of an operation ends, the operation makes a transition from an active to pending state." — [CR-A, history lives-kept](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)
- MIB special start-time values explain the two behaviours: `rttMonScheduleAdminRttStartTime` (TimeTicks, sysUpTime in the future, DEFVAL 0): value 1 = "immediately transition the rttMonCtrlOperState object into 'active' state when the rttMonCtrlAdminStatus object transitions to active"; any value smaller than current sysUpTime (except 1) = "immediately transition ... into 'pending' state ... Also, when the rttMonCtrlOperRttLife counts down to zero (and not when set to zero), this special value causes this conceptual Rtt control row to retransition the rttMonCtrlOperState object into 'pending' state." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Overview-level scheduling summary (config guide): "When scheduling an operation, it can start immediately or start at a certain month, day, and hour. There is a pending option to set the operation to start at a later time." (used for threshold-triggered reactions) — [CG-OV17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_overview.html); [CG-OV15](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_overview-0.html)
- Newer MIB-2016 objects for start type: `rttMonScheduleAdminStartType` {pending(1), now(2), random(3), after(4), specific(5)} DEFVAL pending; `rttMonScheduleAdminStartDelay` Integer32 (500..10000) ms, DEFVAL 500: "For rttMonScheduleAdminStartType with random option, a random time is generated with in provided start delay range and added to current time to generate the random start time of the probe." — [MIB-2016](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)
- Legacy `ip sla monitor schedule` (12.3(14)T–12.4(2)T, 12.2(31)SB2, 12.2(33)SXH) has identical keywords/defaults/usage text (no `random`); replaced by `ip sla schedule` in 12.4(4)T, 12.2(33)SB, 12.2(33)SXI; `rtr schedule` replaced in 12.2(33)SRB. — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)

### Inferences
- Interaction life/ageout for a re-implementation: ageout is a countdown that runs only while the entry is not active (from configuration until start, and again from end-of-life); it is reset to the configured value whenever the entry leaves the active state; reaching zero deletes the whole operation (config + data). With `life forever` the ageout timer can only expire before the first start.
- The CLI's "active → pending after life ends" and the MIB's "active → inactive" are reconcilable via the MIB's start-time special value: a CLI operation scheduled with a start-time that has already passed behaves like the second special value and thus re-enters *pending*; an operation that reached zero life is displayed by `show ip sla application` counters as "inactive Entries" only if it is in the MIB 'inactive' state. Which of the two a specific IOS release displays after life expiry should be verified on a lab device (see Gaps).
- The MIB recurring rule (b) literally rejects ageout=0 (0+life ≤ 86400), whereas the CLI explicitly allows ageout "never (0)"; a re-implementation should follow the CLI rule: `life < 86400` and (`ageout == 0` or `life + ageout > 86400`).

### Gaps
- The CLI numeric ranges for `life seconds` and `ageout seconds` are not printed in the command reference text (only the MIB ranges 0..2147483647 and 0..2073600 are documented); CLI help-string ranges were not captured.
- Exact displayed state after life expiry ("Inactive" vs "Pending" in `show ip sla statistics` / `show ip sla application` counters) could not be confirmed from Cisco documentation.

## 2. Multioperation scheduling — `ip sla group schedule`

### Takeaway
A group schedule spreads N operations evenly across `schedule-period` (start interval = period / N, computed per 1-second slot), restarts them every `frequency` (default = schedule-period, overriding each operation's own frequency), and optionally randomises start offsets and restart frequencies (`frequency range a-b`, min 100 ms spacing). `frequency < schedule-period` causes overlap and is discouraged; `frequency > schedule-period` leaves idle gaps.

### Cited Findings
- Syntax (CR-I): `ip sla group schedule group-id {operation-ids | add operation-ids | delete operation-ids | reschedule} {schedule-period seconds | schedule-together} [ageout seconds] [frequency [seconds | range random-frequency-range]] [life {forever | seconds}] [start-time {hh : mm [: ss] [month day | day month] | pending | now | after hh : mm : ss | random milliseconds}]`; `no ip sla group schedule group-id` = "To cause all the IP SLAs operations belonging to a multioperation schedule to become inactive". — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Arguments: `group-id` "The range is from 0 to 65535."; `operation-ids` "The length of this argument is up to 125 characters. Indicate ranges of operation ID numbers with a hyphen. Individual ID numbers and ranges of ID numbers are delimited by a comma. For example ... 2, 3, 4, 9, 20 / 10-20, 30-35, 60-70 / 2, 3, 4, 90-100, 105-115"; "In Cisco IOS Release 15.2(4)T and later releases and in Cisco IOS Release 15.1(1)T: A single operation ID is a valid option"; `add`/`delete` add/remove IDs from an existing schedule; `reschedule` "Recalculates the start time for each IP SLAs operation within the multioperation schedule based on the number of operations and the schedule period. Use this keyword after an operation has been added to or removed from an existing multioperation schedule."; `schedule-period seconds` "Specifies the amount of time (in seconds) for which the group of IP SLAs operations is scheduled. The range is from 1 to 604800."; `schedule-together` "Starts and runs all of the specified operations at the same time." (15.3(2)S); `ageout` default 0 (never); `frequency seconds` "Specifies the number of seconds after which each IP SLAs operation is restarted. The frequency of all operations belonging to the multioperation schedule is overridden and set to the specified frequency. The range if from 1 to 604800. Note: The default frequency is the value specified for the schedule period."; `frequency range random-frequency-range` "Enables the random scheduler option ... disabled by default. The frequencies at which the IP SLAs operations within the multioperation schedule will restart are chosen randomly within the specified frequency range (in seconds). Separate the lower and upper values of the frequency range with a hyphen (for example, 80-100)."; `life seconds` default 3600; `start-time` "If the start-time is not specified, no information is collected until the start-time is configured or a trigger occurs that performs a start-time now."; `random milliseconds` 0–10000. Default: "The multioperation schedule is placed in a pending state". — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Even-distribution algorithm (CR-I, quoted by WebFetch): "IP SLAs calculates how many operations it should start in each 1-second interval by dividing the number of operations by the schedule period." and "On a Cisco 2600 router, the maximum recommended value of operations per second is 6 or 7 (approximately 350 to 400 operations per minute)." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Reboot behaviour: "When you reboot the router, the IP SLAs multiple operations scheduling functionality schedules the operations in the same order as was done before the reboot. For example ... ip sla group schedule 2 1-20 schedule-period 40 start-time now. Over a range of 40 seconds, 20 operations have to be started (that is, one operation every 2 seconds). After the system reboot, operation 1 will start at t seconds and operation 2 starts at t +2 seconds, operation 3 starts at t +4 seconds, and so on." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Skipping rule: "The IP SLAs multiple operations scheduling functionality schedules the maximum number of operations possible without cancelling. However, this functionality skips those IP SLAs operations that are already running or those that are not configured and hence do not exist. The total number of operations will be calculated based on the number of operations specified in the command, irrespective of the n[umber that exist]". — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Random scheduler rules (CR-I): "The starting value of the frequency range should be greater than the timeout values of all the operations in the multioperation schedule."; "The starting value of the frequency range should be greater than the schedule period."; "The individual operations in a multioperation schedule will be uniformly distributed to begin at random intervals over the schedule period."; "The operations within the multioperation schedule restart at uniformly distributed random frequencies within the specified frequency range."; "The minimum time interval between the start of each operation in a multioperation schedule is 100 milliseconds (0.1 seconds). If the random scheduler option is disabled, the minimum time interval is 1 second."; "Only one operation can be scheduled to begin at any given time. If the random scheduler option is disabled, multiple operations can begin at the same time."; "The first operation will always begin at 0 milliseconds of the schedule period."; "The order in which each operation in a multioperation schedule begins is random." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Add/delete rules (CR-I): "If an operation is added that already belongs to the multioperation schedule, no action is taken."; "If two or more operations are added after the multioperation schedule has started, then the start times of the newly added operations will be uniformly distributed based on a time interval that was calculated prior to the addition of the new operations. If two or more operations are added before the multioperation schedule has started, then the time interval is recalculated based on both the existing and newly added operations."; "If an operation is added to a multioperation schedule in which the random scheduler option is enabled, then the start time and frequency of the newly added operation will be randomly chosen within the specified parameters."; "If an operation is added to a multioperation schedule in which the existing operations have aged out or the lifetimes of the existing operations have ended, the newly added operation will start and remain active for the amount of time specified by the multioperation schedule."; "If the ip sla group schedule group-id reschedule command is entered after an operation is added or deleted, the time interval between the start times of the operations is recalculated based on the new number of operations"; "If an active operation is deleted, then the operation will stop collecting information and become inactive." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Enhanced-history interplay: "15.1(4)M: ... A random scheduler will not schedule an IP SLAs probe for which enhanced-history is configured. A fixed frequency multioperation scheduler will not schedule an IP SLAs probe for which enhanced history is configured if the enhanced-history interval is not a multiple of the scheduler frequency." Before 15.1(4)M "the enhanced-history interval was overwritten and set to a multiple of the scheduler frequency." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Config-guide worked examples (paraphrase of CG-MS17 figures): default (frequency = schedule period): 10 operations, 20-second schedule period → first operation at 0 s, one every 20/10 = 2 s, operation 10 at 18 s, group restarts every 20 s. Schedule period 20 s < frequency 30 s → operations start at 0,2,...,18 s, idle from 19–29 s, second iteration at 30 s. Schedule period 20 s > frequency 10 s → second iteration begins at 10 s before the first finishes: operations 6–10 of cycle 1 overlap operations 1–5 of cycle 2 during 10–18 s; "Not recommended due to inefficient scheduling". More operations than seconds: 10 operations / 5 s → 2 operations per 1-second interval; 10 / 4 s → 2.5 → rounded to 3 in the first seconds, the remainder distributed at the end; minimum spacing 1 s. — [CG-MS17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_multi_scheduler.html)
- Config-guide restrictions: "Do not use the no ip sla group schedule and ip sla group schedule commands consecutively in a configuration file"; operation-ID list max 125 characters including commas; "All operations in a group should have same frequency"; scheduler skips already-running or non-existent operations. Prerequisites: operations must be configured first; decide group membership, traffic type, and frequency. — [CG-MS17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_multi_scheduler.html); also "The frequency of all operations scheduled in a multioperation group must be the same." — [CG-ICMP17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_echo.html)
- Verification outputs (CG-MS17): `show ip sla group schedule` → "Group Entry Number: 1 / Probes to be scheduled: 1-10 / Schedule period: 60 / Group operation frequency: Equals schedule period / Status of entry (SNMP RowStatus): Active / Next Scheduled Start Time: Start Time already passed / Life (seconds): 1200 / Entry Ageout (seconds): never"; `show ip sla configuration` shows "Group Scheduled: TRUE"; `show ip sla statistics` for 20 operations over a 60-s period shows start times 3 s apart (03:06:21.760, 03:06:24.754, 03:06:27.751 ...). ### Inferences
- Implementation formula: start offset of the k-th operation (k = 0..N-1) = floor(k × period / N) seconds when N ≤ period; when N > period, ceil(N / period) operations are started in each 1-second slot. Group `frequency` replaces each member's individual `frequency` for as long as it is in the group.
- Because "Group operation frequency" defaults to the schedule period, the steady state is a strict round-robin: each operation runs exactly once per schedule period.

### Gaps
- Cisco does not document an explicit maximum number of operations per group beyond the 125-character ID string and the global 2000-operation limit (section 8).
- The XE-17 ICMP-echo chapter prints the group syntax with `frequency group-operation-frequency` as if mandatory while the command reference marks it optional; the command reference is taken as authoritative.

## 3. Operation states and the state machine (rttMonCtrlOperState / RowStatus / CLI displays)

### Takeaway
The MIB defines OperState values reset(1), orderlyStop(2), immediateStop(3), pending(4), inactive(5), active(6), restart(7); only pending/inactive/active are real states (reset/orderlyStop/immediateStop/restart are commands). Transitions: schedule start-time arrival or trigger → active; life expiry, stop, `no ip sla group schedule`, ageout or row delete → inactive; reset (or creation without a start time / `no ip sla schedule`) → pending. RowStatus (`Status of entry (SNMP RowStatus)`) is Active once scheduled and notInService otherwise.

### Cited Findings
- `rttMonCtrlOperState` (read-write): "reset(1) - reset this entry, transition to 'pending'; orderlyStop(2) - shutdown this entry at the end of the next RTT operation attempt, transition to 'inactive'; immediateStop(3) - shutdown this entry immediately (if possible), transition to 'inactive'; pending(4) - this value is not settable and this conceptual RTT control row is waiting for further control either via the rttMonScheduleAdminTable or the rttMonReactAdminTable/rttMonReactTriggerAdminTable; This object can transition to this value via two mechanisms, first by reseting this object, and second by creating a conceptual Rtt control row with the rttMonScheduleAdminRttStartTime object with the its special value; inactive(5) - this value is not settable and this conceptual RTT control row is waiting for further control via the rttMonScheduleAdminTable; This object can transition to this value via two mechanisms, first by setting this object to 'orderlyStop' or 'immediateStop', second by the rttMonCtrlOperRttLife object reaching zero; active(6) - this value is not settable and this conceptual RTT control row is currently active; restart(7) - this value is only settable when the state is active. It clears the data of this entry and remain on active state." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Actions on `reset` (MIB): "all rows in rttMonStatsCaptureTable that relate to this conceptual RTT control row are destroyed and the indices are set to 1; if rttMonStatisticsAdminNumHourGroups is not zero, a single new rttMonStatsCaptureTable row is created; all rows in rttMonHistoryCaptureTable that relate to this RTT definition are destroyed and the indices are set to 1; implied history used for timeout or threshold notification ... is purged; rttMonCtrlOperRttLife is set to rttMonScheduleAdminRttLife; rttMonCtrlOperNumRtts is set to zero; rttMonCtrlOperTimeoutOccurred, rttMonCtrlOperOverThresholdOccurred, and rttMonCtrlOperConnectionLostOccurred are set to false; if this causes a change in the value of either of these objects, resolution notifications will not occur; the next RTT operation is controlled by the objects in the rttMonScheduleAdminTable or the rttMonReactAdminTable/rttMonReactTriggerAdminTable; if the rttMonReactTriggerOperState is 'active', it will transition to 'pending'; ... all open connections must be maintained. This can be used to synchronize various RTT definitions, so that the RTT requests occur simultaneously, or as simultaneously as possible." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Actions on transition to `inactive` (MIB): "all statistics and history collection information table entries will be closed and kept; implied history used for timeout or threshold notification ... is purged; rttMonCtrlOperTimeoutOccurred, rttMonCtrlOperOverThresholdOccurred, and rttMonCtrlOperConnectionLostOccurred are set to false ...; the next RTT request is controlled by the objects in the rttMonScheduleAdminTable; if the rttMonReactTriggerOperState is 'active', it will transition to 'pending' ...; all open connections are to be closed and cleanup." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- MIB state/transition table (condensed from the ASCII table; A = pending, B = inactive, C = active): OperState set to reset: A→A, B→inconsistentValue, C→A; set to orderlyStop/immediateStop: A→B, B→B, C→B; event causes trigger state to become active: A→C, B→B, C→C (life not reloaded, note 3); AdminStatus → active with RttStartTime special value 1: A→C, B→C (from C: OperState must first be inactive/pending, note 1); AdminStatus → active with RttStartTime special value < current time (≠1): A→A, B→A; AdminStatus → notInService: A→A, B→B (from C not allowed, note 2); AdminStatus → delete: →B from all; AdminStatus active and RttStartTime arrives: →C from all (from C: life not reloaded, note 3); RowAgeout expires: →B from all; OperRttLife counts down to zero: C→B (N/A from A/B). Notes: "(1) rttMonCtrlOperState must have transitioned to 'inactive' or 'pending' before the rttMonCtrlAdminStatus can transition to 'active'. (2) rttMonCtrlAdminStatus cannot transition to 'notInService' unless rttMonCtrlOperState has been previously forced to 'inactive' or 'pending'. (3) when this happens the rttMonCtrlOperRttLife will not be updated with the rttMonCtrlAdminRttLife." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- RowStatus creation rule: "The conceptual Rtt control row will be placed into a 'pending' state (via the rttMonCtrlOperState object) if rttMonScheduleAdminRttStartTime is not specified." and "This object can be set to 'destroy' from any value at any time." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Stats-table effect of state changes: "If the activity for a conceptual RTT control row ceases because the rttMonCtrlOperState object transitions to 'inactive', the corresponding current hourly group in this table is 'frozen', and a new hourly group is created when activity is resumed. If the activity ... ceases because the rttMonCtrlOperState object transitions to 'pending' this whole table will be cleared and reset to its initial state." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- History-table effect: "A new life will be created when rttMonCtrlOperState transitions 'active'." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Other operational objects: `rttMonCtrlOperModificationTime` "updated whenever an object in the conceptual RTT control row is changed"; `rttMonCtrlOperResetTime` "set when the rttMonCtrlOperState is set to reset"; `rttMonCtrlOperOctetsInUse` (Gauge32, memory used by control+statistics+history rows); `rttMonCtrlOperNumRtts` "total number of probe operations that have been attempted. - CLI display of state: `show ip sla configuration` shows "Next Scheduled Start Time: Start Time already passed | Pending trigger", "Status of entry (SNMP RowStatus): Active | notInService", "Life (seconds): 3600 / Entry Ageout (seconds): never" (or combined "Life/Entry Ageout (seconds): Forever/never"), "Recurring (Starting Everyday): FALSE", "Group Scheduled : FALSE", "Randomly Scheduled : FALSE", "Operation frequency (seconds): 60 (not considered if randomly scheduled)". — [CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)

### Inferences
- CLI ↔ MIB mapping for a re-implementation: `ip sla schedule ... start-time now/absolute/after` = AdminStatus active + RttStartTime (value 1 = now); `start-time pending` / `no ip sla schedule` = RowStatus notInService + OperState pending (clears statistics tables); life countdown to 0 = OperState inactive (tables frozen and kept); `no ip sla group schedule` = inactive; `ip sla restart` = OperState restart(7) (clear data, stay active); `ip sla reset` = rttMonApplReset (engine-wide).
- The MIB description text still says "This status object has six defined values" although seven are enumerated; restart(7) was added later and is the basis of the CLI `ip sla restart`.

### Gaps
- Cisco does not document a CLI display string for every MIB state (e.g. whether `show ip sla statistics` prints "Inactive" or "Pending" for a life-expired non-recurring operation); to be verified in a lab.

## 4. Return codes (RttResponseSense) and success/failure accounting

### Takeaway
RttResponseSense enumerates 0–38: other(0), ok(1), disconnected(2), overThreshold(3), timeout(4), busy(5), notConnected(6), dropped(7), sequenceError(8), verifyError(9), applicationSpecific(10), dnsServerTimeout(11), tcpConnectTimeout(12), httpTransactionTimeout(13), dnsQueryError(14), httpError(15), error(16), mplsLsp*(17–20), enable*(21–29), statsRetrieve*(30–38); the CLI `show ip sla history` "Sense" column uses 1–10. For ICMP echo/path-echo the realistically reachable codes are ok, overThreshold, timeout, busy (pathEcho), dropped, sequenceError, verifyError, plus disconnected/notConnected only for connection-oriented protocols. In the MIB an over-threshold completion is a *completion* (subset of Completions), but the CLI "Number of failures" counter and the "Failed Operations due to over threshold" line treat it as a failure in the one lab sample found (see Gaps).

- Full TC (TC-MIB, verbatim descriptions): "other(0) - the operation is not started or completed or this object is not applicable for the probe type. ok(1) - a valid completion occurred and timed successfully; disconnected(2) - the operation did not occur because the connection to the target was lost; overThreshold(3) - a valid completion was received but the completion time exceeded a threshold value; timeout(4) - an operation timed out; no completion time recorded; busy(5) - the operation did not occur because a previous operation is still outstanding; notConnected(6) - the operation did not occur because no connection (session) exists with the target; dropped(7) - the operation did not occur due to lack of internal resource; sequenceError(8) - a completed operation did not contain the correct sequence id; no completion time recorded; verifyError(9) - a completed operation was received, but the data it contained did not match the expected data; ### Inferences
- Proposed accounting for a Linux re-implementation, consistent with both sources: keep MIB-style counters (Completions incl. over-threshold with RTT accumulated; OverThresholds; Timeouts; Busies; Drops; SequenceErrors; VerifyErrors; Initiations) and derive CLI counters as: Number of successes = Completions − OverThresholds (return code ok), Number of failures = Initiations − successes (everything else, including over threshold), "Failed Operations due to over threshold" = OverThresholds, "Number Of RTT"/RTT Min/Avg/Max = all timed completions (incl. over threshold). This matches the 12.4 lab sample (successes 0, failures 6 with only over-threshold results) and the MIB text; it should be validated against a current IOS XE device.
- For ICMP echo the busy(5) code cannot occur (connectionless echo) because timeout ≤ frequency is enforced; for ICMP path-echo busy can occur (the MIB explicitly warns about small frequency values for pathEcho).

### Gaps
- No Cisco document was found that states explicitly how `Number of successes`/`Number of failures` in `show ip sla statistics` treat overThreshold on current IOS XE 17.x; only the 2009 lab sample and the CLI "Failed Operations due to over threshold" label support "counted as failure". The assignment's premise ("OverThreshold counts as success") is therefore *not* confirmed for the CLI counters (it is true only for the MIB Completions counter).
- Community threads that might contain the exact CLI error text for frequency < timeout could not be retrieved (HTTP 403 for automated fetch); see section 8.

## 5. `history` sub-commands and the history/statistics data model (lives, buckets, samples, filter, distributions, hours, enhanced)

### Takeaway
Two independent stores exist: (a) *statistics* (hourly aggregated groups: hours-of-statistics-kept default 2, range 0–25; distributions-of-statistics-kept default 1, 1–20; statistics-distribution-interval default 20 ms, 1–100) and (b) *snapshot history* (lives-kept default 0 = off, 0–2; buckets-kept MIB default 15 [CLI text says 50], 1–60; samples per bucket 16 (1–30, only >1 for path-echo); filter none|all|overThreshold|failures, default none). *Enhanced history* (`history enhanced [interval 1–3600, default 900] [buckets 1–100, default 100]`) is a third store of sub-hour aggregation buckets.

### Cited Findings
- `history buckets-kept size`: "Number of history buckets kept during the lifetime of the operation. The default is 50." Command default "The default number of buckets kept is 50 buckets." Usage: "Each time IP SLAs starts an operation, a new bucket is created until the number of history buckets matches the specified size or the lifetime of the operation expires. History buckets do not wrap." ... "By default, the history for an IP SLAs operation is not collected. If history is collected, each bucket contains one or more history entries from the operation. When the operation type is Internet Control Message Protocol (ICMP) path echo, an entry is created for each hop along the path that the operation takes to reach its destination. The type of entry stored in the history table is controlled by the history filter command. The total number of entries stored in the history table is controlled by the combination of the samples-of-history-kept, history buckets-kept, and history lives-kept commands." Note: "Collecting history increases the RAM usage. Collect history only if you think there is a problem in the network." Introduced 12.4(4)T replacing `buckets-of-history-kept`. — [CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)
- Contradicting default/range for buckets in the MIB: `rttMonHistoryAdminNumBuckets` Integer32 (1..60), DEFVAL 15: "The maximum number of history buckets to record. When the RttMonRttType is 'pathEcho' this value directly represents a path to a target. For all other RttMonRttTypes this value should be set to the number of operations to keep per lifetime. After rttMonHistoryAdminNumBuckets are filled, the and the oldest entries are deleted and the most recent rttMonHistoryAdminNumBuckets buckets are retained." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB); every `show ip sla configuration` sample prints "Number of history Buckets kept: 15" and auto-template output prints "Max number of history records kept: 15" — [CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html), [CR-A](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)

### Inferences
- Data model for re-implementation: history[life][bucket][sample] with life = one activation (pending→active), bucket = one operation attempt (ICMP echo) or one path exploration (path echo), sample = one hop (1 for echo). Each sample = {SampleTime (uptime at initiation), Address, CompletionTime (0 unless ok), Sense, ApplSpecificSense, SenseDescription}. Filter decides insertion *after* the attempt; lives-kept=0 disables collection *before* the attempt.
- The CLI reference's "default 50 buckets" and "buckets do not wrap" are most likely stale text; MIB DEFVAL 15/range 1–60 with rolling retention is corroborated by every sample output ("Number of history Buckets kept: 15"). A clone should default to 15, cap at 60, and keep the most recent N (index monotonically increasing), but keep "no wrap" as a documented alternative behaviour.

### Gaps
- Cisco documentation does not reconcile "history buckets do not wrap" (CLI) with "most recent buckets are retained" (MIB); behaviour on current IOS XE not verified.
- The upper bound for enhanced-history total memory and what "statistic gathering for the operation ends" means for the *aggregated* statistics (whether normal hourly stats continue) is not documented.

## 7. Aggregated statistics semantics ("Start Time Index" hourly rows, current hour, field meanings)

### Takeaway
Aggregation is per operation, per 60-minute *hourly group* opened when the operation starts (and re-opened on the hour and after each inactive→active resume); the current, still-open hour is included in output ("collected over the past two hours"); each group holds Completions, OverThresholds, Sum, Sum², Max, Min per distribution bucket plus error counters and Initiations; the oldest group is discarded when more than hours-of-statistics-kept groups exist.

### Cited Findings
- Structure (MIB rttMonStatsCaptureTable): "A rolling accumulated history of this information is maintained in a series of hourly 'group(s)'. Each 'group' contains a series of 'path(s)', each 'path' contains a series of 'hop(s)', each 'hop' contains a series of 'statistics distribution bucket(s)'. Each conceptual statistics row has a current hourly group, into which RTT results are accumulated. At the end of each hour a new hourly group is created which then becomes current. The counters and accumulators in the new group are initialized to zero. The previous group(s) is kept in the table until the table contains rttMonStatisticsAdminNumHourGroups groups for the conceptual statistics row; at this point, the oldest group is discarded and is replaced by the newly created one. The hourly group is uniquely identified by the rttMonStatsCaptureStartTimeIndex object." "When the RttMonRttType is 'pathEcho', the path exploration RTT requests' statistics will not be accumulated in this table." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Start Time Index: `rttMonStatsCaptureStartTimeIndex` (TimeStamp) "The time when this row was created. ... The the number of rttMonStatsCaptureStartTimeIndex groups exceeds the rttMonStatisticsAdminNumHourGroups value, the oldest rttMonStatsCaptureStartTimeIndex group will be removed and replaced with the new entry." Entry description: "A list of objects which accumulate the results of a series of RTT operations over a 60 minute time period. ... The second index is a rollover group and it uniquely identifies a 60 minute group." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Freeze/clear rules (repeated): inactive → current group "frozen", new group when resumed; pending → table cleared. — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Per-bucket accumulators (MIB): Completions ("completed without an error and without timing out"), OverThresholds (subset of completions), `rttMonStatsCaptureSumCompletionTime` (Gauge32 ms, "accumulated completion time of RTT operations which complete successfully"), `rttMonStatsCaptureSumCompletionTime2Low/High` ("accumulated squares of completion times (in milliseconds)" split into low/high 32 bits; "the number 4294967296 would have all Low order bits as '0' and the rightmost High order bit will be 1"), `CompletionTimeMax`, `CompletionTimeMin` (ms, successful completions only). Distribution index: "all values that fall above the last interval will be placed into the last interval." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Error counters live in `rttMonStatsCollectTable` ("exact same behavior as the rttMonStatsCaptureTable, except it does not keep statistical distribution information"): NumDisconnects, Timeouts, Busies, NoConnections, Drops, SequenceErrors, VerifyErrors, Address. `rttMonStatsTotalsTable` ("only keeps 60 minute group values"): `rttMonStatsTotalsElapsedTime` "The length of time since this conceptual statistics row was created." and `rttMonStatsTotalsInitiations`. — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Design rationale: "With the new hourly group creation being performed on a 60 minute period, the managing station has plenty of time to collect the data ... the managing station can spread the data gathering over a longer period". — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- CLI: "This command shows information collected over the past two hours, unless you specify a different amount of time using the history hours-of-statistics-kept command." and sample rows headed "Start Time Index: 05:31:12.896 PST Wed Sep 3 2003" (ms-resolution wall-clock time), one row per hourly group (and per path/hop for path echo). — [CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)
- Field meanings for the ICMP echo aggregated rows (from CR-S1 sample plus MIB objects): "Number Of RTT" / "RTT Min/Avg/Max" (successful timed round trips), "Number of successes", "Number of failures", "Failed Operations due to over threshold", "... Disconnect/TimeOut/Busy/No Connection", "... Internal/Sequence/Verify Error" (= Drops/SequenceErrors/VerifyErrors), "Bucket Range: a to < b ms" (last bucket ">=x ms"), "Avg. Latency", "Percent of Total Completions for this range", "Number of Completions/Sum of Latency", "Sum of RTT squared low 32 Bits/ Sum of RTT squared high 32 Bits". — [CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html); [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Hourly-group rollover does not affect `rttMonCtrlOperNumRtts` ("This value is not effected by the rollover of a statistics hourly group."). — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)

### Inferences
- Hour boundaries are relative to the group creation time (row created at operation start, then "at the end of each hour"), not aligned to wall-clock hours; the sample's Start Time Index 05:31:12.896 supports this.
- With hours-of-statistics-kept = 2 the CLI shows the current partial hour plus the previous full hour; "Number of failures" in the aggregated rows is the sum of the per-cause failure counters (plus over-threshold, per the CLI grouping).
- Avg = Sum/Completions; standard deviation = sqrt(Sum²/N − (Sum/N)²) using the 64-bit Sum² (high<<32 | low).

### Gaps
- Whether a group created on `start-time now` is later re-aligned to clock hours, and whether "Start Time Index" of the first group equals the operation start time on IOS XE 17, is not documented.

## 8. Global/general commands, limits and the frequency/timeout/threshold rules

### Takeaway
Global knobs: `ip sla low-memory <bytes>` (default 25 % of system memory; blocks new operations when free memory is below it), `ip sla restart <op>` (clear data of an active operation), `ip sla reset` (engine reset, deletes all IP SLA config), `ip sla logging traps`, `ip sla enable reaction-alerts`, `ip sla key-chain` (MD5 for control messages — irrelevant for ICMP), `ip sla responder` (not needed for ICMP echo); limits: 2000 operations, debug only on first 32; `frequency` default 60 s (MIB 0–604800), `timeout` default 5000 ms (0–604800000), `threshold` default 5000 ms (0–60000), rule frequency(s) > timeout(ms) > threshold(ms); an operation still running when the next is due is skipped and counted as "busy".

### Inferences
- For ICMP echo the enforced invariant is timeout(ms) ≤ frequency(s)×1000 (MIB: frequency cannot be shorter than timeout; timeout cannot exceed frequency) with threshold ≤ timeout; because the echo is asynchronous/connectionless a new probe is never "busy"-skipped, whereas path-echo can be.
- "Estimated system max number of entries" is platform/memory-derived (rttMonApplNumCtrlAdminEntry); the 2000-operation figure in the command reference is the documented CLI maximum and is the safer limit to emulate.

### Gaps
- The exact IOS CLI error strings for violating frequency/timeout/threshold ordering were not obtainable from Cisco documentation.
- The per-operation-type default timeouts ("varies depending on the type") are not enumerated in the timeout command page that was read; for ICMP echo all samples show 5000 ms.

## 9. Time / precision aspects (units, clocks)

### Takeaway
ICMP echo RTT is reported in milliseconds (MIB Gauge32 ms; only UDP jitter with `precision microseconds` reports µs); `precision {milliseconds|microseconds}` exists only for UDP jitter (IOS XE 3.7S+ uses QFP hardware time-stamping); no clock synchronisation is needed for RTT, NTP is required only for one-way (jitter) measurements; history SampleT uses system uptime (ms since 12.4(24)T, centiseconds before), while "Latest operation start time"/"Start Time Index" use wall-clock with ms resolution.

### Cited Findings
- `precision {milliseconds | microseconds}`: "milliseconds: Sets the precision of IP SLAs operation measurements to 1 millisecond (ms). Milliseconds precision is configured by default. microseconds: Sets the precision of IP SLAs operation measurements to 1 microsecond (usec). In Cisco IOS XE Release 3.7S and later releases: Enables IP SLAs QFP Time Stamping." "Note: This command is supported by the IP SLAs User Datagram Protocol (UDP) jitter operation only." "The precision microseconds command requires that both the source and IP SLAs Responder devices are running a version of Cisco IOS software that supports" it. Introduced 12.3(14)T. — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- MIB units: `rttMonLatestRttOperCompletionTime` "The unit of this object will be microsecond when rttMonCtrlAdminRttType is set to 'jitter' and rttMonEchoAdminPrecision is set to 'microsecond'. Otherwise, the unit of this object will be millisecond."; `rttMonHistoryCollectionCompletionTime`, `rttMonStatsCaptureSumCompletionTime`, `CompletionTimeMax/Min` are UNITS "milliseconds". — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- ICMP echo measurement definition: "The ICMP Echo operation measures end-to-end response time between a Cisco router and any devices using IP. Response time is computed by measuring the time taken between sending an ICMP Echo request message to the destination and receiving an ICMP Echo reply." — [CG-ICMP17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_icmp_echo.html)
- RTT computation with responder (not used by ICMP echo): four timestamps; "At the target device, with the responder functionality enabled time stamp 2 (TS2) is subtracted from time stamp 3 (TS3) to produce the time spent processing the test packet"; TS4 "taken at the interrupt level to allow for greater accuracy"; "to capture one-way delay measurements the configuration of both the source device and target device with Network Time Protocol (NTP) is required. Both the source and target need to be synchronized to the same clock source." One-way jitter does not need synchronisation. — [CG-OV17](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_overview.html)
- Time stamps in outputs: history "SampleT = Sample Start Time (milliseconds)" = system uptime (centiseconds before 12.4(24)T); enhanced-history "StartT ... number of milliseconds since the router started"; statistics "Latest operation start time: 07:45:28 GMT Thu Aug 28 2014"; aggregated "Start Time Index: 05:31:12.896 PST Wed Sep 3 2003"; `show ip sla summary` "Stats with u are in microseconds", "Last Run: 20 seconds ago". — [CR-S1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)
- Life countdown granularity: `rttMonCtrlOperRttLife` "is decremented every second". — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)

### Inferences
- A Linux clone for ICMP operations can use a monotonic clock for scheduling/SampleT and wall-clock only for display fields; RTT should be rounded/reported in integer milliseconds to match Cisco's ICMP outputs.

### Gaps
- Whether IOS XE 17.x ICMP echo internally measures sub-millisecond RTT and truncates or rounds to ms is not documented.

### Inferences
- A re-implementation targeting "IOS XE 17.x look-alike" output should use the Engine-III formats (`IPSLAs Latest Operation Statistics`, `Round Trip Time (RTT) for Index n`, `show ip sla summary`) while keeping the MIB object model, which has been stable since 2008 apart from the additive scheduling objects.

### Gaps
- No single Cisco document lists the IOS XE 17.x-specific output layout of `show ip sla statistics aggregated` for icmp-echo; only third-party captures were available.
