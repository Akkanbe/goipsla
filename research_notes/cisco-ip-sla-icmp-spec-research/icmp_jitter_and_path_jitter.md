## KQ1. ICMP Jitter operation mechanics (packet type, timestamps, SD/DS derivation, interval/num-packets, sequence numbers, loss categories, jitter calculation, NTP)

### Takeaway
Cisco documents that `icmp-jitter` sends a burst of ICMP **Timestamp Request (type 13)** packets (default 10 packets, 20 ms apart, repeated every `frequency` seconds) and uses the three RFC 792 timestamps (Originate / Receive / Transmit) plus the local receive time to derive per-direction one-way latency, per-direction jitter (difference of the inter-arrival and inter-departure spacing of two consecutive packets, split into positive and negative jitter), RTT, packet loss (timeouts), successive packet loss, out-of-sequence counts (via the ICMP sequence number and the receive timestamps) and late packets. Cisco does not publish the exact arithmetic for the ICMP variant; it must be inferred from RFC 792 semantics, Cisco's generic jitter formulas for SAA/IP SLAs, and the RTTMON MIB object definitions (see Inferences). One-way latency needs source and destination clocks synchronized (NTP); jitter and loss do not.

#### RFC 792 semantics of the packets used
- Timestamp message format: Type (13 request / 14 reply), Code 0, Checksum, Identifier (16 bit), Sequence Number (16 bit), Originate Timestamp (32 bit), Receive Timestamp (32 bit), Transmit Timestamp (32 bit); timestamps are "32 bits of milliseconds since midnight UT"; "If the time is not available in milliseconds or cannot be provided with respect to midnight UT then any time can be inserted in a timestamp provided the high order bit of the timestamp is also set to indicate this non-standard value."; identifier and sequence number "may be used by the echo sender to aid in matching the replies with the requests" and "may be zero"; the RFC defines the Originate Timestamp as the time the sender last touched the message before sending it, the Receive Timestamp as the time the echoer first touched it on receipt, and the Transmit Timestamp as the time the echoer last touched the message on sending it — [RFC 792, "Timestamp or Timestamp Reply Message"](https://www.rfc-editor.org/rfc/rfc792.txt)
- ICMP Timestamp messages have no data section (fixed 20-byte ICMP message: 8-byte header + 3 × 4-byte timestamps) — [RFC 792](https://www.rfc-editor.org/rfc/rfc792.txt). (Consistent with `request-data-size` not being offered in ICMP jitter configuration mode, see KQ2.)

#### Cisco's generic jitter arithmetic (SAA/IP SLAs, documented with UDP jitter packets)
- "Jitter from source to destination (JitterSD) = (T6-T2) - (T5-T1)" and "Jitter from destination to source (JitterDS) = (T8-T4) - (T7-T3)", worked example "(82 ms - 20 ms) - (60 ms - 0 ms) = 2 ms positive jitter SD", where T1/T5 are the send times of two consecutive packets at the source, T2/T6 their arrival times at the destination, T3/T7 the reply send times at the destination and T4/T8 the reply arrival times at the source — [Cisco, Measuring Delay, Jitter, and Packet Loss with Cisco IOS SAA and RTTMON](https://www.cisco.com/c/en/us/support/docs/availability/high-availability/24121-saa.html)
- Definition used in the `show ip sla statistics` field table: "Jitter is interpacket delay variance."; positive jitter = "network latency increases for two consecutive test packets", negative jitter = "network latency decreases for two consecutive test packets" — [command reference, show ip sla statistics](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s1.html)

### Inferences
- Notation for packet *i* of a burst: `O_i` = Originate timestamp written by the source (source clock), `R_i` = Receive timestamp written by the target, `T_i` = Transmit timestamp written by the target (both target clock, ms since midnight UT), `A_i` = time the reply is received at the source (source clock; Cisco's own internal timestamp, ms). Combining Cisco's description ("difference between interarrival and interdeparture delay for two successive packets") with the SAA formulas gives, for a Linux re-implementation:
  - RTT_i = A_i − O_i (source clock only; no clock sync needed). Cisco does not say whether the target's processing time (T_i − R_i) is subtracted from RTT for ICMP jitter (listed as a gap).
  - One-way SD latency_i = R_i − O_i ; one-way DS latency_i = A_i − T_i (both require the target's clock to be synchronized with the source's; otherwise they are meaningless, which is why Cisco requires NTP and real outputs show 0 samples).
  - SD jitter_i = (R_i − R_{i−1}) − (O_i − O_{i−1}) = SD latency_i − SD latency_{i−1}; DS jitter_i = (A_i − A_{i−1}) − (T_i − T_{i−1}) = DS latency_i − DS latency_{i−1}. A constant clock offset cancels in these differences, which is consistent with Cisco returning jitter values while one-way samples are zero.
  - Sign > 0 → positive jitter (latency increased); < 0 → negative jitter (latency decreased); the MIB keeps per direction the count, sum, sum of squares, min and max of the positive values and of the absolute negative values, and `AvgSDJ`/`AvgDSJ` are "the average of positive and negative jitter values", i.e. the mean of |jitter| over all samples in that direction (the CLI "Jitter Min/Avg/Max" per direction is over |jitter|; the real output shows Min 0, so zero-difference samples are included in the sample count).
  - "Number of SD/DS Jitter Samples" = number of consecutive received packet pairs; with all 10 packets answered it is 9 (as in the real output), i.e. N−1 for N packets when nothing is lost.
- Loss taxonomy implied by the docs/MIB for ICMP jitter: a request with no reply before `timeout` → **Packet Loss** (the direction cannot be known because there is no responder; hence the ICMP-jitter-only reaction element `packetLoss`, "The path of the packets is unknown", and no SD/DS loss counters — see KQ4/KQ5); a reply that arrives after `timeout` → **Packet Late Arrival**; a packet that could not be transmitted → **Packet Skipped** (excluded from the population); consecutive losses are accumulated into "Successive packet loss" and the CLI "Loss Periods Number / Loss Period Length Min/Max / Inter Loss Period Length Min/Max" fields.
- Out-of-sequence: the source compares the ICMP Sequence Number order of replies; using the destination's Receive timestamps it can additionally tell whether the reordering happened on the SD leg (R_i < R_{i−1} while sequence increased), on the DS leg, or in both directions — matching the three CLI counters "Out Of Sequence: Source to Destination / Destination to Source / In both Directions" and the documented "(source-to-destination, destination-to-source, and round-trip)".
- Because RFC 792 timestamps are milliseconds, all ICMP jitter statistics are inherently millisecond-granular (there is no `precision microseconds` for this operation, see KQ2); an implementation must handle the midnight-UT wrap (86,400,000 ms) and the high-order "non-standard" bit (mask it out; the CSR1000V observation suggests IOS itself sets it in the Originate timestamp while still filling ms-since-midnight-UT).

### Gaps
- Cisco does not publish the exact validation rule that decides whether a one-way latency sample is accepted for ICMP jitter (there is no `clock-tolerance` for this operation); the "0 samples when clocks differ" behaviour is only observed in secondary sources.
- Not documented: whether RTT for ICMP jitter subtracts the target processing time (T − R); how "Packet Unprocessed" (shown in real output, see KQ4) is defined; whether the Identifier field carries the operation number; whether a reply with inconsistent (non-monotonic) timestamps is discarded ("Discarded Samples" exists only in path-jitter output).
- No primary Cisco document was found that states whether ICMP jitter one-way values are zeroed or simply not counted when NTP is absent (the explicit statement exists only for UDP jitter).

## KQ2. `icmp-jitter` command syntax, defaults, ranges, and which operation parameters apply / do not apply

### Takeaway
`icmp-jitter {destination-ip-address | destination-hostname} [interval milliseconds] [num-packets packet-number] [source-ip {ip-address | hostname}]` (defaults: interval 20 ms, num-packets 10, source chosen automatically) enters "ICMP jitter configuration (config-ip-sla-icmpjitter)". The command reference's per-command "Command Modes" lists show that `frequency`, `timeout`, `threshold`, `tos`, `vrf`, `tag`, `owner`, `history hours-of-statistics-kept`, `history distributions-of-statistics-kept` and `history statistics-distribution-interval` are available in ICMP jitter mode, whereas `request-data-size`, `verify-data`, `history buckets-kept`, `history filter`, `history lives-kept`, `history enhanced`, `samples-of-history-kept`, `precision`, `clock-tolerance ntp oneway`, `operation-packet priority`, `traffic-class` and `flow-label` are **not** listed for ICMP jitter (the last six/seven are documented as UDP-jitter-only or IPv6-only).

### Cited Findings

#### The `icmp-jitter` command (verbatim from the command reference)
- Syntax: `icmp-jitter {destination-ip-address | destination-hostname} [interval milliseconds] [num-packets packet-number] [source-ip {ip-address | hostname}]`; `destination-ip-address | destination-hostname` "Destination IP address or hostname."; `interval milliseconds` "(Optional) Specifies the time interval between packets (in milliseconds). The default value is 20 ms."; `num-packets packet-number` "(Optional) Specifies the number of packets to be sent in each operation. The default value is 10 packets per operation."; `source-ip {ip-address | hostname}` "(Optional) Specifies the source IP address or hostname. ### Inferences
- The ICMP jitter chapters of the configuration guides (XE 3S, 15M&T, XE 16, XE 17) contain only the "Scheduling IP SLAs Operations" task and no per-parameter table for `icmp-jitter`; the authoritative list of applicable parameters is therefore the union of the "Command Modes" lists above. Effective defaults for a bare `icmp-jitter` operation: interval 20 ms, num-packets 10, frequency 60 s, timeout 5000 ms, threshold 5000 ms, tos 0, no vrf/tag/owner, 2 hours of aggregated statistics, 1 distribution bucket of 20 ms, no history, no enhanced history, millisecond precision.
- `request-data-size` and `verify-data` cannot apply because RFC 792 Timestamp messages carry no data field; this matches their absence from the ICMP jitter mode lists.
- Because the MIB says distribution buckets/intervals are "not applicable to ... jitter probes", the `history distributions-of-statistics-kept` / `statistics-distribution-interval` commands, although accepted in ICMP jitter mode, probably have no effect on jitter statistics (the aggregated jitter tables have no distribution buckets) — treat as optional/no-op in a re-implementation.
- For `threshold`, the wording "for all other IP SLAs operations ... RTT" would put ICMP jitter in the RTT category, and the real `icmp-jitter` output prints "Over Threshold: Number Of RTT Over Threshold: 0 (0%)" (KQ4), i.e. the threshold is compared per packet RTT for ICMP jitter.

### Gaps
- No Cisco document gives an explicit CLI range for `icmp-jitter interval` / `num-packets`; only the MIB range (0..60000 ms) for the interval is available.
- The default `timeout` for ICMP jitter is not stated on the command page ("varies"); 5000 ms comes from the MIB default and one secondary real output.
- Whether the three "history" statistics-distribution commands do anything for ICMP jitter is not documented.

## KQ3. Platforms / releases that support `icmp-jitter`, IOS XE 17.x status, IPv6

### Takeaway
`icmp-jitter` was introduced in Cisco IOS 12.4(6)T (also 12.0(32)SY) and the feature table lists 12.4(6)T and IOS XE 3.8S; it is documented in the IP SLAs configuration guides for IOS XE 3S, 16.x and the IOS XE 17.x "IP Addressing Configuration Guide", and `show ip sla application` lists `icmpJitter` among supported operation types. No Cisco statement of IPv6 support for `icmp-jitter` was found (IPv6 was explicitly added to `path-jitter` in 15.2(3)T / XE 3.7S, but the `icmp-jitter` command history has no such entry and its syntax says only "Destination IP address").

### Inferences
- `icmp-jitter` is best treated as IPv4-only: IPv6 support was added to sibling ICMP operations with explicit command-history entries (path-jitter 15.2(3)T), the icmp-jitter page has none, and no IPv6 header-control command lists the ICMP jitter mode. An IPv6 equivalent would in any case require ICMPv6, which has no Timestamp message type.
- IOS XE 17.x support is established by the presence of the XE 17.x chapter and the unchanged command reference; the exact first XE 17 release is not stated (not needed — supported since XE 3.8S).

### Gaps
- No explicit Cisco sentence "ICMP jitter does not support IPv6" (or "supports IPv6") was found.
- Platform-specific caveats (e.g. Catalyst switches, ASR 9000/IOS XR as *source*) were not researched beyond the IOS-XR-as-target restriction.

## KQ4. `show ip sla statistics` / `show ip sla statistics aggregated [details]` output for an ICMP jitter operation and the meaning of every field (ICMP jitter vs UDP jitter)

### Takeaway

### Inferences
- ICMP jitter cannot attribute a loss to a direction (there is no responder to tell the source whether the request arrived), so the CLI shows a single "Packet Loss" line and the reaction element set contains `packetLoss` ("The path of the packets is unknown") for ICMP jitter but `packetLossSD`/`packetLossDS`/`packetMIA` only for UDP jitter (KQ5). "Tail Drop"/MIA, which for UDP jitter means "lost, direction unknown", is therefore redundant for ICMP jitter and does not appear.
- "Number of successes / Number of failures" count completed *operation runs* (one burst per `frequency`), not packets: 4 successes after roughly four 60-second cycles in the 2021 sample, 1 after one cycle in the 2019 sample; a run fails when its return code is not OK (timeout of the whole operation, busy, internal/sequence/verify error, over threshold — the failure classes listed in the aggregated `details` output).
- "Number Of RTT Over Threshold: n (p%)" = count and percentage of measured RTTs above `threshold` (default 5000 ms) — consistent with the `threshold` command text for non-UDP-jitter operations.
- Expected "aggregated" content for ICMP jitter (not verifiable from Cisco samples): same RTT / one-way / jitter blocks as the UDP jitter aggregate with a direction-less loss line; a re-implementation should aggregate per hour: counts, sums, sums of squares, min, max for RTT, SD/DS one-way, SD/DS positive and negative jitter, plus loss/late/out-of-sequence/skipped counters, successes/failures, busies/errors.
- "Packet Unprocessed" (ICMP jitter only, undefined by Cisco) most plausibly counts replies received but not usable for statistics; treat it as "received but discarded" in a re-implementation and document it as an assumption.

### Gaps
- Cisco provides no field-description table specific to the ICMP jitter layout and no `show ip sla statistics aggregated` sample for ICMP jitter; "Packet Unprocessed", "Loss Periods Number", "Loss Period Length" and "Inter Loss Period Length" are not defined for ICMP jitter (the UDP jitter definitions of the loss-period fields are worded in terms of "resent" packets, which does not literally apply).
- The MIB has no object named for the direction-less ICMP jitter "Packet Loss"; which of `PacketLossSD`/`PacketMIA` IOS populates for `icmpjitter` is undocumented.

## KQ6. ICMP Path Jitter operation (`path-jitter`): syntax, defaults, mechanics, `targetOnly`, statistics, history/aggregation support, limitations

### Takeaway
`path-jitter {destination-ip-address | destination-hostname} [source-ip {ip-address | hostname}] [num-packets packet-number] [interval milliseconds] [targetOnly]` first discovers the hop-by-hop path with a traceroute, then sends N ICMP **echo** probes (default 10) T ms apart (default 20 ms) to every hop, repeating every F seconds (default 60); `targetOnly` skips the trace and probes only the destination. Per hop it reports Latest RTT, Number of RTT, RTT Min/Avg/Max, Number of jitter, Jitter Min/Avg/Max, Packet Loss (Timeouts), Out of Sequence and Discarded Samples — no SD/DS split. It is CLI-only (not in the RTTMON MIB), supports no history, no hourly (aggregated) statistics and no hop information, cannot compensate target processing delay, and the commands `history *`, `samples-of-history-kept`, `lsr-path`, `tos`, `threshold`, `verify-data` are documented as not applicable in path-jitter mode (even though some appear in the command reference mode lists). Introduced as a command in 12.4(4)T (replacing `type pathJitter dest-ipaddr`), IPv6 added in 15.2(3)T / IOS XE 3.7S.

### Cited Findings
- Syntax and keywords (verbatim): `path-jitter {destination-ip-address | destination-hostname} [source-ip {ip-address | hostname}] [num-packets packet-number] [interval milliseconds] [targetOnly]`; `destination-ip-address | destination-hostname` "Destination IP address or hostname."; `source-ip` "(Optional) Specifies the source IP address or hostname. When a source IP address or hostname is not specified, IP SLAs chooses the IP address nearest to the destination."; `num-packets packet-number` "(Optional) Specifies the number of packets to be transmitted in each operation. The default value is 10 packets per operation."; `interval milliseconds` "(Optional) Time interval between packets (in milliseconds). ### Inferences
- Path jitter uses ICMP Echo Request/Reply (type 8/0), not Timestamp messages: the guides say "uses ICMP echoes", the "cannot compensate for target processing delay" restriction only makes sense without timestamps, and `request-data-size`/`verify-data` (payload-based) are offered for it. Hence only RTT-based statistics exist: per-hop jitter is derived from consecutive RTTs and there is no SD/DS split, no one-way latency and no NTP dependency.
- Sample-count arithmetic in Cisco's own example (20 probes → "Number of RTT: 20", "Number of jitter: 2", "Jitter Min/Avg/Max: 2/2/2 ms", RTTs 1/1/3 ms) implies that only non-zero |RTT_i − RTT_{i−1}| differences are counted as jitter samples (one 1→3 and one 3→1 transition), i.e. the path-jitter "jitter" is the absolute difference of consecutive RTTs and zero differences are not counted — unlike ICMP jitter, where zero-valued samples are included (Min 0, N−1 samples).
- "Packet Loss (Timeouts)" = echo probes to that hop with no reply within `timeout`; "Discarded Samples" is undefined by Cisco — plausibly replies that were received but excluded (e.g. late or duplicate); treat as an implementation-defined counter.
- Although the command reference's Command Modes lists include "ICMP path jitter configuration (config-ip-sla-pathJitter)" for `tos`, `threshold`, `verify-data`, `request-data-size` and all `history *` commands, the configuration guide explicitly says most of them "do not apply" in path jitter mode; the guide's list should be treated as authoritative for behaviour (accepted-but-ignored or rejected), and `show ip sla statistics aggregated` / `history` output should not be expected.
- The reaction table (KQ5) lists jitterSDAvg and the SD/DS maxOfPositive/Negative elements for path jitter, but the operation has no per-direction measurement; only rtt, timeout, jitterAvg, packetLateArrival and packetOutOfSequence can be meaningfully evaluated.

### Gaps
- Cisco does not document: the traceroute method/parameters used for path discovery (probe type, max hops, whether the path is re-discovered every cycle), the ICMP identifier/sequence usage, how "Discarded Samples" and "Out of Sequence" are computed per hop, what happens to the per-hop tables when the path changes, or whether `timeout` applies per probe or per hop.
- No field-description table exists for the "Path Jitter Statistics" output.

## KQ7. How Cisco timestamps packets (send/receive timestamps, resolution) — relevance to jitter accuracy

### Takeaway
IP SLAs takes its send/receive timestamps in software on the source and, when the IP SLAs Responder is used (UDP jitter only), at interrupt level on the target so that the target's processing time (TS3−TS2) can be subtracted; ICMP-based operations have no responder, so Cisco states they "can compensate for source processing delay but cannot compensate for target processing delay" and that ICMP jitter accuracy depends on the (unknown) accuracy of the non-Cisco destination. Millisecond precision is the default for all operations; `precision microseconds` (and the XE 3.7S QFP hardware time stamping it enables) exists only for UDP jitter. For ICMP jitter the wire timestamps are RFC 792 millisecond values, so all statistics are millisecond-granular.

### Cited Findings
- "Devices may take tens of milliseconds to process incoming packets, due to other high-priority processes. This delay affects the response times because the reply to test packets might be sitting on queue while waiting to be processed." / "IP SLAs test packets use time stamping to minimize the processing delays. When enabled, the IP SLAs Responder allows the target device to take two time stamps both when the packet arrives on the interface at interrupt level and again just as it is leaving, eliminating the processing time." / "Four time stamps are taken to make the calculation for round-trip time. At the target device, with the responder functionality enabled time stamp 2 (TS2) is subtracted from time stamp 3 (TS3) to produce the time spent processing the test packet as represented by delta. This delta value is then subtracted from the overall round-trip time." / "Notice that the same principle is applied by IP SLAs on the source device where the incoming time stamp 4 (TS4) is also taken at the interrupt level to allow for greater accuracy." / "An additional benefit of the two time stamps at the target device is the ability to track one-way delay, jitter, and directional packet loss." — [IOS XE 17.x IP SLAs Overview, "Response Time Computation for IP SLAs"](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_sla_overview.html); same text in [IOS 15M&T IP SLAs Overview](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/configuration/15-mt/sla-15-mt-book/sla_overview-0.html)

### Inferences
- For a Linux re-implementation of ICMP jitter: take the source send timestamp as late as possible before transmit and the receive timestamp as early as possible (e.g. `SO_TIMESTAMP`/`SO_TIMESTAMPNS` on the raw socket, or hardware timestamps), which is the software analogue of Cisco's interrupt-level TS1/TS4; the target's R/T timestamps are whatever the target's ICMP stack writes (on Linux the kernel writes both in the ICMP timestamp reply path, so T−R is typically 0–1 ms), which is exactly the "accuracy of a non-Cisco destination cannot be determined" caveat.
- Because RFC 792 timestamps are integer milliseconds, sub-millisecond precision can only apply to RTT (source-side timestamps) and never to one-way or per-direction jitter values; Cisco's decision to restrict `precision microseconds` to UDP jitter is consistent with this.
- Path-jitter (ICMP echo) RTTs include the target's echo processing time, so per-hop jitter includes per-hop processing-time variance ("approximates").

### Gaps
- A sentence "This time stamping is made with a granularity of sub-milliseconds" appeared in a search snippet attributed to Cisco IP SLAs overview text but is not present in the XE 17.x overview page and could not be verified verbatim before the fetch quota was exhausted; treat as unverified.
- Cisco does not document where in the IOS/IOS XE software path the ICMP jitter Originate timestamp and the reply receive timestamp are taken (process level vs interrupt level vs QFP), nor whether the `optimize timestamp` / QFP time stamping features affect ICMP jitter (the command text ties them to UDP jitter only).
