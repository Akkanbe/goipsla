## Key Question 1 — ICMP Echo operation: what is timed, what is in the payload, request-data-size default/range vs on-wire size, verify-data, data-pattern

### Takeaway
An ICMP Echo operation is a timed RFC 792 Echo Request/Echo Reply exchange from the source device to the target (no Responder involved); Cisco documents the RTT as "the time taken between sending an ICMP Echo request message to the destination and receiving an ICMP Echo reply", reported in milliseconds. The default request size is 28 bytes of "ARR data portion", and the MIB states that the on-wire packet is IP header (20) + ICMP header (8) + 8 bytes of internal timestamps + request size, i.e. 64 bytes by default.

### Inferences
- On-wire size for the defaults: 20 (IPv4) + 8 (ICMP) + 8 (internal timestamps) + 28 (request-data-size) = 64 bytes, which is exactly the "64-byte IP packet" in the CLI doc; so `request-data-size N` produces an ICMP data field of 8 + N bytes and an IPv4 packet of 36 + N bytes. For a Linux implementation, the "8 internal timestamps" are best modelled as an 8-byte send-timestamp/sequence area at the start of the ICMP data, followed by N bytes of pattern fill (the 0xABCDABCD pattern on Engine-III per [FRR]).
- Because the ICMP target simply echoes the payload, verify-data can only be implemented as a byte-for-byte comparison of the echoed data (and size) against what was sent; a mismatch yields return code verifyError(9), the sample is counted as a failure (Verify Error counter) and no RTT is recorded.
- The MIB's "minimum request size for echo and pathEcho is 28 bytes" conflicts with the CLI text "Range is from 0 to the maximum supported by the protocol"; the CLI text and MIB range (0..16384) suggest the CLI accepts smaller values, but the MIB minimum is the safer floor to emulate.
- Since only the source device timestamps ICMP echo (no Responder), the RTT is TS4−TS1 as measured on the source, with TS4 taken "at the interrupt level"; a Linux re-implementation should use kernel receive timestamps (SO_TIMESTAMP/SO_TIMESTAMPNS) to approximate this.

### Gaps
- Cisco does not publish the byte layout of the 8 "internal timestamps" in the ICMP data (format, endianness, epoch) nor whether a sequence number is embedded in the ICMP Identifier/Sequence fields or in the data; no primary or secondary source with a packet capture of an IP SLA ICMP echo request was reachable (Cisco Community threads returned HTTP 403).
- The exact CLI-enforced minimum/maximum of `request-data-size` for icmp-echo (e.g. whether the CLI shows `<0-16384>`) is not stated in the command reference; only the MIB range (0..16384) and MIB minimum (28) are documented.
- No official Cisco document was found that states the default icmp-echo data pattern ("0xABCDABCD"); it rests on a secondary real-device capture [FRR] plus the config-guide step "range 0 to FFFFFFFF".

## Key Question 2 — Full syntax and semantics of the configuration commands that apply to icmp-echo (with defaults, ranges, units)

### Takeaway
All parameters below are documented in the IOS IP SLAs Command Reference; the key defaults are frequency 60 s, timeout 5000 ms (per MIB DEFVAL; CLI doc says "varies by operation"), threshold 5000 ms, request-data-size 28 bytes, tos 0, traffic-class 0, flow-label 0, no owner/tag/vrf, verify-data off, history not collected (lives-kept 0), 2 hours of statistics, 1 distribution bucket of 20 ms.

### Inferences
- The effective defaults an implementation should reproduce for an icmp-echo operation with no optional commands are those printed by `show ip sla configuration` (see Key Question 6): timeout 5000 ms, ToS 0x0, request size 28, verify-data No, frequency 60 s, life forever/3600 s depending on schedule, ageout never, threshold 5000 ms, 2 hours of statistics, 1 distribution bucket of 20 ms (Engine-III) or 5 buckets of 10 ms (the Engine-II sample), 0 history lives, 15 history buckets, history filter None.
- The CLI doc's "buckets-kept default 50" is contradicted by the MIB DEFVAL 15 and by every `show ip sla configuration` sample ("Number of history Buckets kept: 15"); an implementation should default to 15.
- The Cisco "life" and "ageout" model (pending → active → inactive, life countdown in seconds, ageout suspended while active) must be part of the scheduler if `show ip sla statistics`' "Operation time to live" is to be reproduced.

### Gaps
- The official `frequency (IP SLA)` entry does not state a range; the 1–604800 s range is from a secondary source and the MIB (0..604800). Whether IOS rejects `frequency 0` is undocumented.
- The CLI-enforced range and default of `history lives-kept` per operation type ("dependent on the type of operation") is not given; the MIB allows 0..2.
- `source-interface` behaviour (which address is chosen when the interface has several) is not documented beyond "Specifies the source interface for the operation".

## Key Question 3 — Documented relationship between frequency, timeout and threshold

### Takeaway
Cisco's rule for non-jitter operations (including icmp-echo and path-echo) is (frequency seconds) > (timeout milliseconds) > (threshold milliseconds); timeout may not exceed frequency (the CLI and the MIB both refuse it), and threshold must not exceed timeout. If an operation is still running when the next frequency tick arrives, the run is skipped and a "busy" counter is incremented.

### Cited Findings

For the IP SLAs UDP jitter operation, the following guidelines are recommended: (frequency seconds) > ((timeout milliseconds) + N) … (timeout milliseconds) > (threshold milliseconds) … For all other IP SLAs operations, the following configuration guideline is recommended: (frequency seconds) > (timeout milliseconds) > (threshold milliseconds)" — [CR-A1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html) (frequency entry); repeated verbatim in the timeout and threshold entries — [CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)

- Late replies after timeout count as sequence errors: "a response was received after it had timed-out" is listed as a cause of rttMonStatsCollectSequenceErrors — [MIB](https://github.com/librenms/librenms-mibs/blob/master/CISCO-RTTMON-MIB)
- Recommended minimum frequency: "We recommend that you do not set the frequency value to less than 60 seconds because the potential overhead from numerous active operations could significantly affect network performance." — [CR-A1](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_a1.html)

### Inferences
- Because timeout (ms) ≤ frequency (s × 1000) is enforced at configuration time, a single icmp-echo operation can never have two outstanding requests; a late reply arriving after the timeout window must be discarded (sequence error) rather than attributed to the next cycle.
- Threshold is a statistics classifier only (over-threshold count, overThreshold return code, history filter overThreshold); it does not generate traps unless `ip sla reaction-configuration … react rtt` is configured.

### Gaps
- Cisco does not document the exact CLI error text when timeout > frequency or threshold > timeout is entered.

## Key Question 5 — ICMP Path Echo operation: path discovery, per-hop measurement, syntax, paths/hops/samples, lsr-path, defaults, statistics semantics

### Takeaway
Path Echo first discovers the path with "the traceroute facility" and then pings (ICMP echo) each hop in turn, recording an RTT per hop and per discovered path; the MIB limits statistics to 128 paths and 30 hops (CLI defaults 5 paths, 16 hops, 16 samples), lsr-path can force a loose-source-routed path of up to 8 hops, and the MIB itself warns that per-hop delay differences are heuristic.

### Inferences
- The documented model is two phases per cycle: (1) path discovery via traceroute (Cisco does not specify the probe type; the standard Cisco IOS `traceroute` uses UDP probes with incrementing TTL, but the MIB/CLI text only says "traceroute facility"), (2) one timed ICMP echo request/reply to each discovered hop, in path order, each subject to the same `timeout` and `request-data-size`, with the result stored under (path index, hop index) and the hop address recorded.
- Since a whole path-echo cycle is a single "operation" (NumRtts increments once) that runs sequentially over up to 30 hops, the cycle can exceed `frequency`; in that case the next cycle is skipped and Busies is incremented — hence the MIB's rule frequency > timeout × expected hops.
- Distinct hop sequences observed within the same hourly statistics group become distinct "paths" (index 1..paths-of-statistics-kept); index 1 is also the catch-all "source to target" path for errors that cannot be attributed to a discovered path.
- Threshold/timeout reactions (traps) must be evaluated only on the final-target hop, not on intermediate hops.

### Gaps
- Cisco does not document the traceroute probe type (UDP vs ICMP), the TTL stepping, the number of probes per TTL, the per-probe timeout used during discovery, whether discovery happens every cycle or is cached, or how many ICMP echoes are sent per hop per cycle (the aggregated samples show one completion per hop per cycle, suggesting one).
- The official path-echo `show ip sla configuration` sample prints "Packet Interval/Number of Packets: 20 ms/10" although no such commands are documented for path-echo; the meaning of these fields for path-echo is undocumented.
- Whether `hops-of-statistics-kept` (16 default, 30 max) also caps the traceroute hop discovery depth is not stated.

## Key Question 9 — Version notes (12.4T / 15.x vs IOS XE 16.x/17.x; legacy syntax)

### Inferences
- For compatibility, a re-implementation should accept the modern syntax (`ip sla N` → `icmp-echo …`/`path-echo …`) and optionally the legacy `ip sla monitor N` → `type echo|pathEcho protocol ipIcmpEcho …` form; the semantics and defaults did not change between them.

### Gaps
- No IOS XE 16/17 release note documenting a behavioural change to icmp-echo or path-echo (beyond platform support) was found; differences appear limited to `show` formatting and the `data-pattern` line.

## Key Question 10 — Official Japanese terminology (Cisco Japanese edition)

### Takeaway
Cisco Japan's translated IP SLA configuration guide (IOS XE 16.10) supplies official Japanese terms for both operations and every parameter's purpose text; command keywords stay in English.

### Cited Findings
- ICMP Echo operation = "ICMP エコー動作" (ICMP echo operation); description: "ICMP エコー動作は、Cisco ルータと IP を使用する任意のデバイスの間のエンドツーエンド応答時間を測定します。応答時間は、ICMP エコー要求メッセージを宛先に送信してから ICMP エコー応答を受信するまでの時間を測定して算出されます。" (The ICMP Echo operation measures end-to-end response time between a Cisco router and any device using IP. Response time is computed by measuring the time taken between sending an ICMP Echo request message to the destination and receiving an ICMP Echo reply.) "IP SLA ICMP エコー動作と ICMP ping テストは同じ IETF 仕様に準拠しているので、どちらの方法でも同じ応答時間が得られます。" (The IP SLA ICMP Echo operation conforms to the same IETF specifications for ICMP ping testing, and the two methods result in the same response times.) restriction: "RFC 862 のエコー プロトコルをサポートするネットワーキング デバイスであれば使用できますが、シスコのネットワーキング デバイスを宛先デバイスとして使用することを推奨します。" (Any networking device that supports the RFC 862 Echo protocol can be used, but using a Cisco networking device as the destination device is recommended.) note: "宛先デバイスで IP SLA Responder を設定する必要はありません。" (The IP SLA Responder does not need to be configured on the destination device.) — [JA-ECHO](https://www.cisco.com/c/ja_jp/td/docs/ios-xml/ios/ipsla/configuration/xe-16-10/sla-xe-16-10-book/sla-xe-16-10-book_chapter_01111.html)
