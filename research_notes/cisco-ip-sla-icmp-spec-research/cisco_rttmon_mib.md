## Q0. Which module versions exist, how do the copies differ, and where are the OID roots?

### Takeaway
The authoritative CISCO-RTTMON-MIB is at `{ ciscoMgmt 42 }` = 1.3.6.1.4.1.9.9.42 with LAST-UPDATED 2016-04-14 (compliance Rev23); the TC module is 1.3.6.1.4.1.9.9.485 and the ICMP extension is 1.3.6.1.4.1.9.9.486 (its tables hang under the main MIB's rttMonStats/rttMonLatestOper arcs). Cisco's 2022 GitHub copy adds a `pathJitter(27)` RttMonRttType value that older mirrors (LibreNMS) lack.

### Inferences
- An AgentX re-implementation only needs to register the 1.3.6.1.4.1.9.9.42 subtree (plus the .485/.486 module-identity nodes, which carry no objects); the ICMP extension objects live inside the .42 subtree, so a single agent module can serve all three MIBs.
- Because the 2022 Cisco copy adds `pathJitter(27)` without bumping LAST-UPDATED, tooling that validates MIB revisions may consider LibreNMS's copy "same version" while lacking the enum; a re-implementation should load Cisco's GitHub copy.

### Gaps
- I did not find a Cisco-published changelog explaining when/why `pathJitter(27)` was added to the TC module (the revision history was not updated).

## Q1. Textual conventions (CISCO-RTTMON-TC-MIB) — exact enumerations

### Takeaway
All enumerations needed for ICMP operations are in CISCO-RTTMON-TC-MIB: RttMonRttType echo(1)/pathEcho(2)/icmpjitter(16) (+pathJitter(27) in 2022 copy), RttMonProtocol ipIcmpEcho(2)/icmpJitterAppl(34), RttResponseSense 0..38, RttMonReactVar 1..49, RttMonScheduleStartType 1..5, RttMonTargetAddress = raw OCTET STRING (4 octets for ipIcmpEcho).

- For a Linux implementation supporting only ICMP operations, rttMonApplSupportedRttTypesTable should report echo(1), pathEcho(2), icmpjitter(16) (and pathJitter(27) if the newer TC is adopted) as valid, and rttMonApplSupportedProtocolsTable should report ipIcmpEcho(2) and icmpJitterAppl(34).

### Inferences
- The "28 bytes" ICMP default is the ICMP payload the operator specifies; on the wire an IOS ICMP echo is 20 (IP) + 8 (ICMP) + 8 (Cisco internal timestamps) + 28 = 64 bytes, and the 8-byte timestamp block is why the minimum request size is 28 rather than 0.
- rttMonEchoAdminPktDataResponseSize should simply mirror rttMonEchoAdminPktDataRequestSize for ipIcmpEcho ("set by the agent to match").
- For ICMP jitter, the applicable configuration set is Protocol=icmpJitterAppl(34), TargetAddress, SourceAddress, PktDataRequestSize, Interval, NumPackets, TOS/Dscp, VrfName, Precision (and the NTP tolerance objects when one-way values are computed).

### Gaps
- No authoritative statement was found on how IOS encodes an IPv6 target in rttMonEchoAdminTargetAddress (the TC only defines 4 octets for ipIcmpEcho; the IPv6 feature doc says MIB support was "not modified"). A 16-octet encoding is a plausible but unverified assumption.

## Q5. Scheduling — rttMonScheduleAdminTable and rttMonGrpScheduleAdminTable

### Takeaway
rttMonScheduleAdminTable (AUGMENTS the control row) defines life (DEFVAL 3600 s; 2147483647 = forever), start time (TimeTicks vs sysUpTime; special value 1 = start immediately, any past value = pending), ageout (deprecated ConceptRowAgeout DEFVAL 3600; current ConceptRowAgeoutV2 DEFVAL 0 "to be consistent with CLI ageout default"), daily recurrence and the newer StartType/StartDelay random-start objects; rttMonGrpScheduleAdminTable is the MIB face of `ip sla group schedule` (multioperation scheduler) with Probes list, Period, Frequency/FreqMin/FreqMax, Life, Ageout, StartTime, Add/Delete/Reset and StartType/StartDelay.

## Q7. Statistics and history collection configuration — rttMonStatisticsAdminTable, rttMonHistoryAdminTable

### Takeaway
rttMonStatisticsAdminTable (AUGMENTS control row) sizes the hourly statistics store: NumHourGroups (0..25) DEFVAL 2, NumPaths (1..128) DEFVAL 5, NumHops (1..30) DEFVAL 16, NumDistBuckets (1..20) DEFVAL 1, DistInterval (1..100 ms) DEFVAL 20 — note the MIB DEFVALs for paths/hops are 5/16, not 1/1. rttMonHistoryAdminTable sizes the per-sample history: NumLives (0..2) DEFVAL 0, NumBuckets (1..60) DEFVAL 15, NumSamples (1..30) DEFVAL 16, Filter DEFVAL none; the CLI command reference's "history buckets-kept ... default is 50" conflicts with both the MIB DEFVAL (15) and the show output (15).

- On the "50 vs 15" question: the MIB DEFVAL is 15, the current show output prints 15, and only the command-reference prose says 50 (inherited from the old `buckets-of-history-kept` text). A MIB-compatible implementation should use 15.
- The MIB's per-hour rollover ("At the end of each hour a new hourly group is created") plus NumHourGroups=2 means the ICMP echo statistics store is a 2-slot ring keyed by the sysUpTime at group creation.

### Gaps
- Cisco's `history buckets-kept` default discrepancy (50 vs 15) is not explained by any source found; it could be a documentation carry-over error or a platform difference.

### Inferences
- For ICMP echo (RttType echo) the agent needs rows: rttMonStatsCaptureTable with PathIndex=1, HopIndex=1 and DistIndex 1..NumDistBuckets; rttMonStatsCollectTable/rttMonStatsTotalsTable with the same StartTimeIndex; a completed echo increments Completions (and OverThresholds when > rttMonCtrlAdminThreshold), adds to SumCompletionTime and the 64-bit SumCompletionTime2, updates Min/Max, and increments Initiations; a timeout increments rttMonStatsCollectTimeouts and Initiations only.
- The DistIndex bucket for a completion time t is min(floor(t / DistInterval) + 1, NumDistBuckets), per the bucket example (0–9 ms → bucket 1 with interval 10 ms).
- "Hour group" rollover must be driven by wall-clock hour elapsed since group creation (60 minutes), not by NumRtts; the StartTimeIndex is the sysUpTime at creation, and only NumHourGroups groups are retained (oldest discarded).
- For ICMP jitter rows the hourly aggregate lives in rttMonIcmpJitterStatsTable (Q11), not rttMonJitterStatsTable (whose entry text restricts creation to RttType jitter).

### Gaps
- Fifteen counter objects cite "the special behavior as defined by the ROLLOVER NOTE in the DESCRIPTION of the ciscoRttMonMIB object", but no such note exists anywhere in the module DESCRIPTION text of the 2022 Cisco copy (verified by grep); the intended behaviour (presumably wrap-around at 2147483647) is undocumented.
- The MIB does not say whether the hour groups are aligned to clock hours or to 60 minutes from activation; the text only says "At the end of each hour a new hourly group is created".

## Q11. CISCO-RTTMON-ICMP-MIB — rttMonLatestIcmpJitterOperTable and rttMonIcmpJitterStatsTable

### Takeaway
The ICMP extension defines two tables inside the main subtree: rttMonLatestIcmpJitterOperTable (1.3.6.1.4.1.9.9.42.1.5.4, 50 objects, all Gauge32 except the sense code, UNITS milliseconds/packets/occurrences) for the last ICMP-jitter operation, and rttMonIcmpJitterStatsTable (1.3.6.1.4.1.9.9.42.1.3.8, 59 objects, Counter32 accumulators + Gauge32 min/max/averages) for hourly aggregates; rows exist only when rttMonCtrlAdminRttType = icmpjitter(16) and rttMonEchoAdminProtocol = icmpJitterAppl(34). There is no NTP-state or UnSyncRTs object in the ICMP tables, and packet loss is a single undirected counter (PktLoss) plus directional out-of-sequence counters and min/max successive-loss run lengths.

### Inferences
- The ICMP jitter tables differ from the UDP jitter tables in four ways an implementation must respect: (1) every numeric object carries an explicit UNITS clause of milliseconds (no microsecond precision option is expressed), (2) loss is undirected (PktLoss/PktLosses, plus successive-loss min/max) instead of PacketLossSD/DS/MIA, (3) there is no MOS/ICPIF/NTPState/UnSyncRTs object, (4) sum-of-squares accumulators are split into *Lows/*Highs Counter32 pairs in the stats table but are single Gauge32 objects in the latest-operation table.
- rttMonIcmpJStatsOverThresholds counts operations violating the jitterAvg reaction threshold (not rttMonCtrlAdminThreshold), unlike rttMonStatsCaptureOverThresholds.
- Because `pathJitter(27)` exists only as an enum and the feature guide says path jitter is unsupported in the MIB, an implementation should treat pathJitter rows as CLI/API-only (or expose only the control row) rather than inventing statistics tables.

### Gaps
- The ICMP MIB does not define the per-hop or one-way clock-sync semantics (NTP tolerance objects exist only in rttMonEchoAdminTable and apply "only for jitter operation with precision of microsecond"); whether IOS applies them to ICMP jitter one-way values is not documented in the sources read.
- CLI `show ip sla statistics` field names for ICMP jitter were not captured verbatim (the fetched guide summary omitted them), so the exact show-output-to-object mapping is inferred from object names.

Eight notifications live under rttMonNotifications = 1.3.6.1.4.1.9.9.42.2.0: four legacy per-condition traps (.1 connection change, .2 timeout, .3 threshold, .4 verify error; all deprecated, each carrying rttMonCtrlAdminTag, rttMonHistoryCollectionAddress and the relevant rttMonCtrlOper*Occurred flag), the generic rttMonNotification (.5, deprecated) and its replacement rttMonNotificationV2 (.8, current) that carry rttMonReactVar/Occurred/Value/ThresholdRising/ThresholdFalling plus rttMonEchoAdminLSPSelector and the (Long)Tag, and two MPLS LPD notifications (.6, .7) out of scope. Every trap is sent on both the violation and its clearing (the Occurred flag changing value).

- Conformance: ciscoRttMonMibComplianceRev23 lists ciscoNotificationGroupRev1 among MANDATORY-GROUPS, ciscoNotificationGroupRev2 "only mandatory for the devices that support MPLS", and ciscoNotificationGroupRev3 "optional for receiving notifications containing rttMonCtrlAdminLongTag". — [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)
- The Occurred-flag semantics that gate the legacy traps and the rttMonReactVar timeout/connectionLoss/verifyError reactions are in rttMonCtrlOperTable (Q8) and rttMonReactOccurred/rttMonReactValue (Q6): rttMonReactOccurred becomes true when "rttMonReactVar is set to timeout and rttMonCtrlOperTimeoutOccurred set to true", "connectionLoss and rttMonCtrlOperConnectionLostOccurred set to true", "verifyError and rttMonCtrlOperVerifyErrorOccurred is set to true", or "For all other values of rttMonReactVar, if the corresponding value exceeds the configured rttMonReactThresholdRising", and false on the reverse conditions (below rttMonReactThresholdFalling); rttMonReactValue "holds the actual value that violated the configured threshold values" and "will be always 0" for timeout/connectionLoss/verifyError. Reset/inactive transitions clear the flags but "resolution notifications will not occur". — [MIB](https://raw.githubusercontent.com/cisco/cisco-mibs/main/v2/CISCO-RTTMON-MIB.my)
- CLI enabling: `ip sla enable reaction-alerts` (default "IP SLAs notifications are not sent to registered applications") and `ip sla logging traps` (default "SNMP system logging messages specific to IP SLAs trap notifications are not generated"); reaction traps are configured per operation with `ip sla reaction-configuration ... action-type {none | trapOnly}` (plus `snmp-server enable traps` in IOS, not covered here). — [Cisco Command Reference, I through P](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)

### Inferences
- Because rttMonHistoryCollectionAddress is a varbind of every trap and is indexed by { rttMonCtrlAdminIndex, life, bucket, sample }, an agent must emit an instance OID for it even when history is off (the MIB says the instance "will not be valid" but still lists it); the safest compatible behaviour is to use the current life/bucket/sample indices (or .N.0.0.0-style placeholders) and fill the value with the target address for echo/pathEcho and a zero-length string otherwise.
- For an ICMP-only agent, the current, non-MPLS notification set to implement is rttMonNotificationV2 (mandatory-optional per Rev3 group) and, for legacy managers, rttMonNotification; the four per-condition legacy traps are deprecated but still present in IOS-era managers' trap definitions.

### Gaps
- The MIB does not state whether an agent should send rttMonNotification and rttMonNotificationV2 both, or only one; IOS's actual selection (likely version-dependent) was not verified.

## Q13. CLI ↔ MIB mapping, limits, and conformance notes relevant to ICMP operations

### Takeaway
`show ip sla configuration` is a direct rendering of the control row: "Entry number" = rttMonCtrlAdminIndex (1..2147483647), "Status of entry (SNMP RowStatus)" = rttMonCtrlAdminStatus (Active / notInService), and the other lines map one-to-one onto rttMonCtrlAdmin/EchoAdmin/ScheduleAdmin/StatisticsAdmin/HistoryAdmin objects. CLI defaults and MIB DEFVALs differ in three notable places (request size 28 vs DEFVAL 1, ageout 0 vs deprecated DEFVAL 3600, history buckets doc 50 vs DEFVAL/show 15); capacity is bounded by rttMonApplNumCtrlAdminEntry (IOS: 2000 operations) and rttMonApplProbeCapacity; compliance Rev23 lists the groups an ICMP implementation must support and refines Frequency/port ranges.

### Inferences
- A MIB-faithful Linux agent should present CLI-style defaults through the MIB (request size 28 for ICMP, ageout 0, history buckets 15, paths 5, hops 16, samples 16) while still accepting the MIB DEFVAL semantics for the deprecated objects; the RowStatus shown in the CLI is exactly rttMonCtrlAdminStatus, so `notInService` rows must exist as createAndWait/notInService rows in the table.
- For an ICMP-only implementation the mandatory conformance groups that matter are the control/stats/history/latest-oper/appl/notification groups; Ethernet/MPLS/voice/video/Y.1731/Fabric-Path groups are conditional and can be omitted.
- Path jitter can only be modelled as a control row with RttType pathJitter(27) (no statistics/history tables), consistent with the feature guide's "not supported in the RTTMON MIB" statement.

### Gaps
- No Cisco document was found that formally maps each `show ip sla configuration` line to a MIB object; the mapping table above is derived from object semantics.
- The exact object lists of the newer mandatory groups (ciscoCtrlGroupRev28, ciscoStatsGroupRev8–10, ciscoCtrlGroupRev24/25) were not transcribed; implementers should read those OBJECT-GROUP clauses from the module text when building a conformance checklist.
- IOS behaviour for reading rttMonApplNumCtrlAdminEntry/rttMonApplProbeCapacity on a specific platform (actual numbers) was not verified against a device.
