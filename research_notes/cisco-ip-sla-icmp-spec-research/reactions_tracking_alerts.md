## KQ1. `ip sla reaction-configuration`: full semantics, threshold-type algorithms, defaults, ranges, and the one-event-per-transition rule

### Takeaway
The command attaches one or more "reactions" (monitored element + threshold-type + rising/falling thresholds + action) to an operation; every threshold-type is evaluated per completed operation (measurement) and maintains a boolean "occurred" state (`rttMonReactOccurred`) that flips to true on the rising condition and back to false on the falling condition; a notification/trigger is generated only on those flips, never repeatedly while the value stays over the rising threshold. Defaults: threshold-type `never`, action-type `none`, `consecutive 5`, `xofy 5 5`, `average 5`, count range 1–16 each, `threshold-value` default for rtt 5000/3000 ms (other elements have element-specific defaults, see KQ2).

### Inferences
- Per-measurement state machine for a re-implementation (derived from the MIB text): keep for each reaction row a boolean `occurred` (init false), a window of the last y results (xofy), a consecutive counter, and an averaging buffer of size N. On each completed measurement: compute `violation = value > rising` when `occurred == false`, or `below = value < falling` when `occurred == true`; apply the type rule (immediate: single sample; consecutive: N successive samples of the same kind; xofy: at least x of the last y samples of the same kind; average: mean of the last N samples compared to rising (to set) / falling (to clear)); emit "rising" event when `occurred` flips false→true and "falling" event when it flips true→false. This is the only reading consistent with the MIB "Conversely ..." clauses plus the config-guide figure (no repeated events while continuously over threshold).
- The CLI docs describe only "violates the upper threshold or lower threshold"; the MIB's per-type "Conversely" clauses are the only documented clear semantics (e.g., `consecutive` clears only after N consecutive below-falling results; `immediate` clears on the first below-falling result). A developer should implement the MIB semantics.
- Values are compared as integers (Integer32 thresholds); "exceeds"/"rises above" and "falls below" suggest strict comparisons (`>` rising, `<` falling), but Cisco does not document boundary behaviour (see Gaps).
- For timeout/connectionLoss/verifyError, the "value" is the boolean `rttMonCtrlOperTimeoutOccurred` / `...ConnectionLostOccurred` / `...VerifyErrorOccurred`, so `consecutive N` on `timeout` means N consecutive timed-out operations set the event and N consecutive completed operations clear it; `average` is rejected for these elements.

### Gaps
- Boundary condition (value exactly equal to rising or falling threshold) is not documented anywhere found (CLI says "exceeds"/"drops below"; MIB says "rises above"/"falls below"; treat as strict).
- Whether the `average` window uses a sliding window over the last N results or a tumbling window is not stated; the CLI example ("the last three results") implies sliding.
- For `xofy`, whether the window of y is shared between the rising and falling evaluation (or reset on transition) is not documented.
- Whether the rising and falling thresholds must satisfy lower <= upper is not stated in the CLI reference; no parser error text was found (defaults such as `jitterAvg 100/100` show equal values are legal).

## KQ3. `ip sla reaction-trigger`: semantics, pending state, run length, `show ip sla reaction-trigger`

### Takeaway
`ip sla reaction-trigger <op> <target-op>` links a monitoring operation to a target operation that must be scheduled in the pending state; when a reaction with action-type `triggerOnly`/`trapAndTrigger` fires, the target moves pending→active. Before 15.2(3)T the target then runs for its full configured `life` and cannot be re-triggered until that life ends; from 15.2(3) the target runs until the condition-cleared event, then stops and returns to Pending so it can be triggered again.

### Cited Findings
- Syntax/purpose: "To define a second Cisco IOS IP Service Level Agreements (SLAs) operation to make the transition from a pending state to an active state when one of the trigger action type options are defined with the ip sla reaction-configuration command, use the ip sla reaction-trigger command in global configuration mode. To remove the trigger combination, use the no form of this command." `ip sla reaction-trigger operation-number target-operation` / `no ip sla reaction-trigger operation`. operation-number: "Number of the operation for which a trigger action type is defined"; target-operation: "Number of the operation that will be triggered into an active state." ## KQ4. `ip sla logging traps`, `ip sla enable reaction-alerts`, syslog messages, SNMP notifications (CISCO-RTTMON-MIB), `snmp-server enable traps`, and `show ip sla reaction-configuration`

### Takeaway
Reactions can be delivered three ways: (1) syslog messages, enabled per device by `ip sla logging traps`; (2) SNMP notifications `rttMonNotification` (OID 1.3.6.1.4.1.9.9.42.2.0.5, carrying rttMonReactVar/rttMonReactOccurred/rttMonReactValue/rising/falling) or the four deprecated per-condition notifications, enabled by `snmp-server enable traps rtr` (and/or CISCO-SYSLOG-MIB traps via `snmp-server enable traps syslog`); (3) in-box event publication to registered IOS processes (EEM, tracking) via `ip sla enable reaction-alerts`. Cisco's support matrix: RTT violations in non-jitter operations → SNMP trap only; RTT (RTTAvg) in jitter operations and all other non-boolean elements → syslog only; timeout/connectionLoss/verifyError → both.

### Cited Findings

## KQ5. Legacy per-operation form (`threshold-type`/`action-type` on the operation, `rtr reaction-configuration`) vs. the newer `react` form, and how the operation-level `threshold` relates to reaction thresholds and the OverThreshold return code

### Takeaway
The operation-level `threshold <ms>` (default 5000, range 0–60000) only drives statistics and the OverThreshold return code/counters ("This value is not used for generating SNMP trap notifications"); reaction thresholds are separate per-reaction values (`threshold-value upper lower`, default 5000/3000 for rtt). The legacy model (rtrReactionAdmin objects / `rtr reaction-configuration`) had a single per-operation reaction using rttMonCtrlAdminThreshold as the rising value and `threshold-falling` as the falling value; from 12.3(14)T (`ip sla monitor reaction-configuration ... react`) and 12.4(4)T (`ip sla reaction-configuration`) reactions are per element with their own thresholds.

### Cited Findings
- `threshold (IP SLA)`: "To set the upper threshold value for calculating network monitoring statistics created by a Cisco IOS IP Service Level Agreements (SLAs) operation, use the threshold command ..." `threshold milliseconds` — "Length of time required for a rising threshold to be declared, in milliseconds (ms). Range is 0 to 60000. Default is 5000." Usage: "The value specified for this command must not exceed the value specified for the timeout command. The threshold value configured by this command is used only to calculate network monitoring statistics created by a Cisco IOS IP SLAs operation. This value is not used for generating Simple Network Management Protocol (SNMP) trap notifications. Use the ip sla reaction-configuration command in global configuration mode to configure the thresholds for generating IP SLAs SNMP trap notifications. ... For the IP SLAs User Datagram Protocol (UDP) jitter operation, the threshold (IP SLA) command sets the upper threshold value for the average jitter calculation. For all other IP SLAs operations, the threshold (IP SLA) command sets the upper threshold value for the round-trip time (RTT) measurement. IP SLAs will calculate the number of times the average jitter or RTT measurement exceeds the specified threshold value." — [CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)

### Inferences
- Two independent threshold mechanisms must be implemented: (a) operation `threshold` → sets return code OverThreshold (vs OK) for a completed probe and increments over-threshold counters/distribution buckets; (b) reaction rows → rising/falling event generation. ## KQ6. Object tracking: `track <n> ip sla <op> {state | reachability}`, delay, timers, `show track`, use-cases

### Takeaway
Tracking evaluates the operation's latest return code: `state` is Up only for OK; `reachability` is Up for OK or OverThreshold; every other code (Timeout etc.) is Down. The tracking process polls IP SLA objects at a default 5-second interval (`track timer ip sla`, range 1–3000 s or 500–5000 ms); `delay up/down` (0–180 s, default 0) postpones client notification; clients (static routes, HSRP/VRRP/GLBP, PBR, EEM) act on Up/Down transitions.

### Cited Findings
- Syntax: `track object-number ip sla operation-number [state | reachability]` / `no ...`; object-number "The range is from 1 to 1000."; `state` — "(Optional) Tracks the operation return code."; `reachability` — "(Optional) Tracks whether the route is reachable."; Default: "IP SLAs tracking is disabled."; mode: global configuration; history: 12.4(20)T introduced ("replaces the track rtr command"), 12.2(33)SXI1, XE 2.4, 12.2(33)SRE; 15.1(3)T / 15.1(1)S / 12.2(50)SY object range increased to 1000. — [EOT-CR-T](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipapp/command/iap-cr-book/iap-t1.html)

### Inferences
- "Latest operation return code" displayed values seen in official outputs: `OK`, `over threshold`, `Unknown` (before the first result). For an ICMP echo operation the practically relevant codes are OK, OverThreshold (RTT > operation `threshold`), Timeout (no reply within `timeout`), plus error codes; a re-implementation should expose the latest `RttResponseSense` per operation and let a tracker map it with the two rules above.
- The tracked value is the latest completed operation's return code, sampled by the tracker at its polling interval (default 5 s); there is no hysteresis other than `delay up/down`. Because ICMP echo default frequency is 60 s, the tracker will see a Timeout only after the next scheduled probe times out, so failover latency ≈ frequency + timeout + delay down (+ ≤ poll interval).
- For path-echo, only the target's result affects the return code used for tracking (MIB: timeouts/thresholds for intermediate hops do not change the Occurred objects).

### Gaps
- Cisco documents tracking as a polled object (5 s default) but does not state whether IP SLA additionally pushes results to the tracker (`ip sla enable reaction-alerts` / `show ip sla event-publisher` "react-alert" registration); which mechanism is used in practice is unverified.
- No official page fetched for PBR `set ip next-hop verify-availability <ip> <seq> track <n>` or HSRP/VRRP `track <n> decrement` semantics; only the "Tracked by: HSRP Ethernet0/1 3" / "Static IP Routing 0" client names appear in the outputs above.
- The exact list of return-code strings printed by `show track` (e.g. "Timeout", "Verify error") is not documented.

## KQ7. EEM integration: `event ipsla`, reaction-type values, and built-in variables

### Takeaway
`event ipsla` (12.4(22)T / 12.2(33)SRE) publishes an EEM event when an IP SLA reaction fires (both "occurred" and "cleared" conditions); the event carries operation id, group name, condition (cleared/occurred), reaction type, destination address, rising/falling thresholds, measured value and threshold counts. The applet-side `$_ipsla_*` variable names are only evidenced by community usage, but the Tcl `event_reqinfo` keys are official.

### Cited Findings
- Syntax: `event [tag event-tag] ipsla {group-name name [operation-id operation-id-value] | operation-id operation-id-value [group-name name]} [dest-ip-address ip-address] [reaction-type type] [maxrun maxruntime-number]` / `no event [tag event-tag] ipsla`; operation-id-value "Number in the range from 1 to 2147483647."; `dest-ip-address` "(Optional) Specifies the destination IP address for which the IP SLAs events are monitored."; `reaction-type type` values: connectionLoss, icpif, jitterAvg, jitterDSAvg, jitterSDAvg, maxOfNegativeDS, maxOfNegativeSD, maxOfPositiveDS, maxOfPositiveSD, mos, packetLateArrival, packetLossDS, packetLossSD, packetMIA, packetOutOfSequence, rtt, timeout, verifyError (each with the same one-line description as the react keywords); `maxrun` default 20 seconds, `maxruntime-number` ssssssss[.mmm] 0–31536000 s; Default: "No events are published when IP SLAs operations are triggered."; mode applet configuration; history 12.4(22)T, 12.2(33)SRE; Usage: "An EEM event is published when an IP SLAs reaction is triggered. Either the group-name or the operation-id must be specified. The remaining parameters are optional."; example `event ipsla group-name grp1 dest-ip-address 209.165.200.221 reaction-type timeout maxrun 3`. — [EEM-CR](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/eem/command/eem-cr-book/eem-cr-e1.html)
- Tcl registration: `event_register_ipsla [tag ?] group_name ? operation_id ? [reaction_type ?] [dest_ip_addr ?] [queue_priority low|normal|high|last] [maxrun ?] [nice 0|1]` — "Registers for an event that is triggered by the event ipsla command. - Applet built-in variables (secondary evidence only): `$_ipsla_condition` ("The value of 'Occurred' is what you'll see when the threshold is crossed"), `$_ipsla_react_type`, `$_ipsla_oper_id`, `$_ipsla_measured_threshold_value`, `$_ipsla_threshold_rising`, `$_ipsla_dest_ip_addr`; "the built-in variables available when an applet policy is triggered by the IPSLA event detector can be viewed using the show event manager detector command with the detailed keyword." — [Cisco Community: EEM $_ipsla_condition variable states](https://community.cisco.com/t5/network-management/eem-ipsla-condition-variable-states/td-p/2585489), [RouterDiscussions: EEM Applet Using IPSLA ED](https://www.routerdiscussions.com/viewtopic.php?t=961) (both as summarised by search; community page returns 403 to direct fetch)

### Inferences
- The EEM event is emitted on both edges of the reaction state machine (condition = occurred on rising, cleared on falling), consistent with the MIB `rttMonReactOccurred` transitions; `measured_threshold_value` corresponds to `rttMonReactValue`, `threshold_count1/2` to CountX/CountY.
- Applet variable names follow EEM's `_<detector>_<key>` convention, so `_ipsla_group_name`, `_ipsla_oper_id`, `_ipsla_condition`, `_ipsla_react_type`, `_ipsla_dest_ip_addr`, `_ipsla_threshold_rising`, `_ipsla_threshold_falling`, `_ipsla_measured_threshold_value` are the expected set; this is inferred from the Tcl keys plus community usage, not from an official table.

### Gaps
- No official Cisco table of the ipsla event detector's applet built-in variables was found (the XE 17.x and 15M&T "Writing EEM Policies Using the Cisco IOS CLI" tables contain no `_ipsla_` rows).
- Whether `event ipsla` requires `ip sla enable reaction-alerts` is not stated explicitly in the EEM reference (only implied by the reaction-alerts command text).

## KQ8. Cisco best-practice / tuning notes for thresholds and timers

### Takeaway
Cisco's documented rules are: frequency (s) > timeout (ms) > threshold (ms) for non-jitter operations; for UDP jitter frequency > timeout + num-packets × interval, and timeout > threshold; timeout should equal max expected RTT plus processing time and may not exceed frequency; the operation `threshold` is for statistics only, while reaction thresholds are configured separately; MOS thresholds use the 100–500 encoding; triggers are diagnostic tools, not for normal operation.

### Cited Findings
- "Consider the following guidelines before configuring the frequency (IP SLA), timeout (IP SLA), and threshold (IP SLA) commands. For the IP SLAs User Datagram Protocol (UDP) jitter operation, the following guidelines are recommended: (frequency seconds) > ((timeout milliseconds) + N) ; (timeout milliseconds) > (threshold milliseconds) where N = (num-packets number-of-packets) * (interval interpacket-interval). ... For all other IP SLAs operations, the following configuration guideline is recommended: (frequency seconds) > (timeout milliseconds) > (threshold milliseconds)" — [CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html) (both `threshold (IP SLA)` and `timeout (IP SLA)` entries)
- `timeout milliseconds` "Range is 0 to 604800000." "We recommend that the value of the milliseconds argument be based on the sum of both the maximum round-trip time (RTT) value for the packets and the processing time of the IP SLAs operation." "The value specified for the timeout (IP SLA) command cannot be greater than the value specified for the frequency (IP SLA) command." "The default timeout value varies depending on the type of IP SLAs operation you are configuring." — [CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)
- `threshold milliseconds` "Range is 0 to 60000. Default is 5000." "The value specified for this command must not exceed the value specified for the timeout command." — [CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)
- MIB constraints: `rttMonCtrlAdminTimeout` (ms, 0..604800000, DEFVAL 5000): "The value of this object cannot be set to a value which would specify a duration exceeding rttMonCtrlAdminFrequency."; `rttMonCtrlAdminFrequency` (s, 0..604800, DEFVAL 60): "This object cannot be set to a value which would be a shorter duration than rttMonCtrlAdminTimeout. ... When the rttMonCtrlAdminRttType object is defined to be 'pathEcho', the suggested value for this object is greater than rttMonCtrlAdminTimeout times the maximum number of expected hops to the target." and busy handling: "it may happen that the next RTT operation is blocked by a RTT operation which has not yet completed. In this case, the value of a counter (rttMonStatsCollectBusies) ... is incremented in lieu of initiating a RTT operation, and the next attempt will occur at the next rttMonCtrlAdminFrequency expiration." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Reaction thresholds are separate from the operation threshold: "This value is not used for generating Simple Network Management Protocol (SNMP) trap notifications. Use the ip sla reaction-configuration command ... to configure the thresholds for generating IP SLAs SNMP trap notifications." — [CR-S2](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_s2.html)
- xofy sanity rule: "NOTE: When x > y, the probe will never generate a reaction." — [MIB](https://raw.githubusercontent.com/librenms/librenms/master/mibs/cisco/CISCO-RTTMON-MIB)
- Triggers: "Triggers are usually used for diagnostics purposes and are not intended for use during normal operation conditions." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Y.1731 note (non-ICMP, for completeness): "if any changes are made to the reaction configuration for the supported react type variables while the probe is in active state or if the reaction configuration itself is removed for an active probe, then it is recommended to restart the probe for the configuration change to take effect." — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- MOS example guidance: "send an SNMP logging trap when the MOS value exceeds 4.9 (best quality) or falls below 2.5 (poor quality)" → `threshold-value 490 250`. — [CR-I](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/ipsla/command/sla-cr-book/sla_i1.html)
- Recommended defaults used in Cisco's failover technote: threshold 5000 ms, timeout 5000 ms, frequency 60 s. — [TECHNOTE](https://www.cisco.com/c/en/us/td/docs/ip/ip-routing/200785-ISP-Failover-with-default-routes-using-I.html)

### Inferences
- A re-implementation should validate: 0 ≤ threshold ≤ timeout ≤ frequency×1000 (reject `timeout > frequency` as IOS does), and warn when x > y in xofy.
- Default reaction thresholds (rtt 5000/3000) intentionally straddle the default operation threshold (5000) so that the default `react rtt` never fires unless RTT exceeds the operation threshold.

### Gaps
- Cisco does not publish guidance on choosing `threshold-value` lower vs upper spread (hysteresis width) or on interaction between `consecutive`/`xofy` counts and the tracking `delay` timers.
